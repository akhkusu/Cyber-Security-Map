# パスワード管理・認証アプリ 製品別補完仕様

版: 1.1 / 調査日: 2026-11-13

この文書は `PRODUCT-SPEC.md` の7・8・11・12・14・17章を補完する必須仕様です。製品名を列挙しただけでは対応完了としません。具体的な操作・保存先・復旧・移行・利用テストを一つの単位として実装します。既存の製品を利用する人にも、OS組込みの機能だけを使う人にも対応します。

Google・Apple・Bitwardenの製品固有条件と、認証・復号・権限・セッション・削除の追加契約は[モデルの再監査](MAJOR-PLATFORMS-MODEL-AUDIT.md)を併用します。特に、基盤Accountへログインできることと暗号化されたデータを使えることを区別します。

「全製品に対応済み」という主張はしません。現行の機能・料金・対応OSを確認したレシピを登録する仕組みを持ち、追加候補と実装済みの製品を分けます。利用者が使っている製品がない場合にも、安全に保留・追加調査へ進めます。

## P2. 製品・機能・インスタンスのモデル

### P2.1 別物として管理する対象

1. 提供者へのログインアカウント。
2. 一つ以上のパスワード保管庫。
3. その保管庫を開く方式。
4. 端末上のアプリ・拡張機能の利用場所。
5. 認証アプリ、または保管庫内のTOTP保存機能。
6. パスキー・物理キーの保存先。
7. 同期に使うクラウドアカウント。
8. 暗号化されたバックアップファイルと、別に保管する解除情報。
9. 復旧用メール、電話、紙の情報、管理者・家族による復旧。

同じ製品でも個人用・仕事用、別サーバー・別保管庫・別プロフィールを区別します。同じスマホ上の二つのアプリを、独立した二台の端末として数えません。同期された同じ秘密の複製と、別の認証方式も区別します。

永続化モデルは少なくとも次を表現できるものとします。これは論理的なモデルであり、互換性のために既存のキーへ追加する形でも構いません。

| 記録 | 必要な属性 |
| --- | --- |
| 製品の利用場所 | ランダムなID、製品ID、本人が選んだ所有区分、利用する端末・プロフィール、基盤Account、保存モード |
| 保管庫 | ランダムなID、製品の利用場所、解除方式の種類、保存先の種類。解除情報そのものは持たない |
| 認証情報の保存先 | ランダムなID、TOTP／パスキー／物理キー等の種類、対象Account、保存するアプリ・保管庫・端末、同期グループ |
| 予備・バックアップ | 種類、対象、本人が区別できる保管場所の区分、復元に必要なものへの関係、保管確認日と動作確認日 |
| 関係 | 始点・終点、関係の種類、本人の確認日時、根拠の種別、未確認・確認済み・利用できないの区別 |
| 作業 | 対象ID、機能ID、安定したステップID、適用したレシピ版、利用者の記録、取り消しに必要な直前状態 |

「ない」「使えない」「分からない」「まだ聞いていない」を同じfalseへ潰しません。登録対象と認証方式は別に識別し、同じ物理キーを複数Accountへ登録しても、各Account側の登録完了は個別に確認します。旧データにこれらの属性がない場合は未確認として追加し、既存の完了記録は消しません。

### P2.2 レシピが宣言する能力

`productId`、`featureId`、`accountType`、`vaultType`、`platform`、`osRange`、`appVersionRange`、`browser`、`distributionChannel`、`region`、`planRequirement`、`adminRequirement`を条件にします。

`featureId`には少なくとも次を用意します。

- manager.install、account.sign-in、vault.create、vault.unlock、vault.lock。
- manager.generate、manager.save、manager.fill、manager.update-login。
- manager.root-authentication、manager.emergency-information、manager.backup、manager.restore。
- authenticator.install、token.enroll、token.use、token.sync、token.export、token.restore、token.migrate。
- passkey.register、passkey.use、passkey.backup-access。

名前が同じ「ログイン」でも、提供者へのサインインと保管庫の復号を別ステップにします。`not-supported`、`not-reviewed`、`admin-controlled`、`not-applicable`、`not-chosen`は別の状態にします。

## P4. 選択・導入・既存利用の分岐

### P4.1 選択時に聞くこと

1. すでに使っているマネージャーがあるか。ある場合はその製品を優先して点検する。
2. 使う端末・ブラウザー。必要な違いがあるときだけ聞く。
3. OS組込みの製品を使いたいか、複数OSをまたぐ必要があるか。
4. 仕事・学校の指定や、家族の管理権限があるか。
5. 選択に必要な場合だけ、クラウド同期・ローカル保存・無料／有料の希望を聞く。

全製品の長い比較記事を読ませて決めさせません。候補を絞る場合は「持っている端末で使える」「必要な機能が確認できている」など、具体的理由を示します。料金・機能・対応OSが未確認なら、選択の根拠にしません。セキュリティの架空の総合点や宣伝順位を付けません。

### P4.2 既存利用の点検

新規登録や既存のマスター変更を無条件に要求しません。アプリを開ける、同期先を確認できる、必要な保管庫がある、重要なログインが利用できる、復旧の準備がある、という状態を一つずつ確認します。既存の利用が確認できれば対応する導入ステップを省略します。

複数製品を併用している場合、既定の自動入力先、重要なアカウントの保存先、同じ情報の更新漏れを確認します。利用者が意図した併用を「間違い」と扱わず、どちらへ保存したか分からない状態を解消します。

### P4.3 公式の導入経路

正規の公式サイト・アプリストア・公式拡張ストアへ案内します。検索広告の最上位をインストール先にしません。発行者・製品名・OS・ブラウザーを確認できる説明を出します。似た名前の第三者アプリと区別します。組織端末で導入が禁止されている場合は管理者確認へ進みます。

インストール後にはアプリを開く、正しいアカウントへサインインする、対象の保管庫を開く、という確認が必要です。外部の有料契約は本人が条件を確認して行い、ガイドが自動契約しません。

## P5. Apple「パスワード」の専用仕様

Apple組込みのマネージャーは、追加アプリを使いたくない人の正式な選択肢です。「別製品をインストールしなければ対策できない」という扱いにしません。

### P5.1 適用条件と役割

Appleの資料では、専用の「パスワード」アプリはiOS 18 / iPadOS 18 / macOS Sequoia / visionOS 2以降の系統で案内されています。旧OSの設定内のパスワード管理と分岐します。Apple端末とWindowsのiCloud Passwordsでは手順と機能を同一視しません。[公式概要](https://support.apple.com/en-gb/120758)

独立した「マスターパスワードを新しく作る」という共通ステップを表示しません。Apple Accountのサインイン、端末の解除、Keychainへのアクセス、他サービスのパスワードを区別します。

### P5.2 必須の利用経路

1. 操作する端末と、利用するApple Accountを確認する。
2. 端末ロックとApple Accountの2ファクタ認証の既存記録を再利用する。
3. 「パスワード」アプリを開けることを確認する。
4. 同期を使う場合は、iCloudのPasswords & Keychainの状態と、そのAccountを本人が確認する。
5. 重要なアカウントの保存項目を選ぶか追加する。
6. 固有のパスワードの生成・保存・公式サイト側の設定を一つずつ案内する。
7. Safari・対応アプリ等の自動入力で実際にログインできることを確認する。
8. 別端末で使いたい人だけ、その端末の同期と利用を確認する。
9. 信頼できる端末・電話番号や、Apple Account復旧の備えを確認する。
10. Apple Accountの認証情報をKeychainだけから取り出せる設計にしない。独立した復旧の備えへ接続する。

Windowsでは、iCloud for Windows、iCloud Passwordsアプリ、対応するブラウザー拡張の設定をそれぞれ分けます。Appleの資料はWindows上のパスワード管理・確認コードを案内していますが、パスキーの全機能がApple端末と同じだとは仮定しません。[Windows管理](https://support.apple.com/en-mt/guide/icloud-windows/icwa812f1681/icloud)

### P5.3 確認コードの保存

他サービスのTOTPを保存する場合は、対象項目→確認コードの設定→QRまたは設定キー→サービス側の確認→予備手段、の順にします。Apple Account自身の復旧を、同じApple Accountが必要な唯一の確認コードへ依存させません。[確認コードを含む公式概要](https://support.apple.com/en-gb/120758)

### P5.4 共有・書き出し・削除

共有グループは任意機能です。共有する内容と相手を本人が理解できる別の操作にします。個人用を仕事用のグループへ自動追加しません。書き出しファイルの形式・秘密の保護・パスキーや共有項目の含まれ方を個別に確認し、「全部が復元可能」と保証しません。

## P6. Google Password Managerの専用仕様

1. Chromeのプロフィールと保存に使うGoogle Accountを確認する。Gmailのログインと別アカウントの場合も扱う。
2. 端末内だけの保存と、アカウントに保存した情報を区別する。
3. Androidの画面ロックと、他の端末で使うGoogle Password Manager PINを同じ秘密として説明しない。
4. 保存されたログインを一つ選び、生成・変更・保存・自動入力を確認する。
5. パスキーは保存先・同期・端末ロック・別端末からの利用を分けて確認する。
6. Google Accountが開けない場合にも使える独立した復旧・予備ログインを確保する。
7. Chromeのプロファイル削除、端末初期化、Googleアカウントからの削除の影響を区別する。
8. パスワード書き出しとパスキー移行を同じ機能と仮定しない。

現行のGoogle資料は、Androidでは端末の画面ロック、ほかの環境ではGPM PIN等の違いを説明しています。アプリは一律に「マスターを作る」手順を挿入しません。[パスキー管理](https://support.google.com/chrome/answer/13168025)、[GPM PIN](https://support.google.com/chrome/answer/16608973)

## P7. NordPassの専用仕様

NordPassでは、Nord Accountへのログイン用情報と、保管庫を開くマスターパスワードを分けます。MFAはNord Accountに作用し、保管庫のマスター復旧コードも別の役割です。[情報の種類](https://support.nordpass.com/hc/en-us/articles/360008866077-Passwords-and-codes)

### P7.1 必須の利用経路

1. 個人用・家族用・組織用と、対象のNord Accountを確認する。
2. 既存アカウントと保管庫を再利用するか、新規作成するかを選ぶ。
3. Nord Accountへのログインを確認する。
4. マスターによる保管庫の解除と、任意の生体認証の役割を確認する。
5. マスターを作る場合は現行の公式条件と、より長い固有のパスフレーズの作り方を表示する。
6. マスター復旧用の情報を紙等の独立した場所へ保管する。以前の復旧コードを再生成すると無効になる点を、その操作前に示す。
7. Nord AccountのMFAを、認証アプリまたは対応キーで設定・確認する。
8. MFAの復旧と、保管庫のマスターを忘れた場合の復旧を別々に用意する。
9. 重要ログインを生成・保存・利用する。
10. 別端末・拡張機能を必要に応じて設定し、利用を確認する。

公式資料ではマスター復旧に24文字のコードを使う経路が案内されています。コードを失った場合の保管庫のリセットには内容の削除を伴うため、通常の「復旧成功」として勧めません。[マスター復旧](https://support.nordpass.com/hc/en-us/articles/360002376657-What-if-I-forgot-my-NordPass-Master-Password)、[データを消すリセットの説明](https://support.nordpass.com/hc/en-us/articles/5388857973905-How-to-reset-NordPass-account)

MFA設定ではNordPassからNord AccountのManage MFAへ移る手順を明示します。コードは公式画面だけに入力します。[MFA設定](https://support.nordpass.com/hc/en-us/articles/360002770497-How-to-enable-Multi-Factor-Authentication-MFA)

## P8. Proton Pass・1Password・Bitwarden・ローカルDBの追加条件

### P8.1 Proton Pass

Proton Mail・Pass・Authenticatorは製品名が違っても、同じProton Accountの認証に依存する場合があります。本人が選んだ同一Accountなら認証設定を共有しますが、Mailを開くための秘密やコードがPassやAuthenticatorだけにあり、その同期にも同じAccountが必要になる構成を検出します。

任意の追加パスワードは、Proton AccountのパスワードやMFAとは別です。有効化時の再サインインと、忘れた場合の回復可能範囲を先に確認する経路を定義します。追加パスワードを有効にしただけで、AccountのMFAを完了にしません。[追加パスワード](https://proton.me/support/pass-extra-password)

アカウントのパスワード復旧と、暗号化済みデータへのアクセス復旧の違いも確認します。復旧ファイルだけでアカウントへのサインインも戻るとは説明しません。[公式の復旧方式](https://proton.me/support/set-account-recovery-methods)

### P8.2 1Password

通常のアカウントパスワード＋Secret Key、製品が提供する別のログイン方式、組織SSOを分けます。Emergency Kit、アカウント復旧コード、認証アプリの予備の秘密、家族・管理者による復旧を同じ「復旧コード」にまとめません。復旧コードだけでMFAを省略できるとは案内しません。

登録情報の変更後に緊急用情報を更新する必要があるかを確認します。別端末の再承認、共有保管庫、仕事用データの所有者、家族を退会した場合のアクセスも、本人に必要な場合だけ質問します。

### P8.3 Bitwarden

米国・EU・セルフホストを区別し、既存データのある地域を再利用します。通常のマスター、パスキー等による利用、組織のSSO・管理方式を分けます。個人用へ組織の復旧機能が使えると約束しません。

Bitwarden Password Managerの統合TOTPと、独立したBitwarden Authenticatorを別に選べるようにします。後者でも、保護対象の同じ保管庫へコードを同期したら独立性を失うことがあります。公式資料は、Bitwarden自身の2FAにはローカルコードとして保つことを説明しています。[Authenticatorの違い](https://bitwarden.com/help/bitwarden-authenticator/)

### P8.4 KeePass系・ローカルDB

保管庫のファイル、解除パスフレーズ、任意のキーファイル、任意のハードウェア資格情報を分けます。ファイルを別の端末へコピーするだけで解除できるとは扱いません。キーファイルを追加する場合、紛失時に開けない条件と別保管を先に案内します。

KDBXの版・端末側アプリ・ブラウザー連携・同期サービス・競合解消を確認します。DBとキーファイルを同じ同期先だけに置いて「独立した二要素」と表示しません。古いDBを上書きせず、複製で復元を試します。[KeePassXCガイド](https://keepassxc.org/docs/KeePassXC_UserGuide)、[キーファイルの公式FAQ](https://keepassxc.org/docs/)

## P9. マネージャー共通の必須テスト

製品ごとに少なくとも次を定義します。

- 新規利用と既存利用。既存の重要ログインを失わない。
- ロック解除できることと、外部アカウントへログインできることを別に確認する。
- 生成時の長さ・文字条件を、そのサービスの制約に合わせる。公開例文を使わない。
- 保存後の実ログインと更新後の保存内容の一致。
- 自動入力が出ない、誤ったアカウントが候補に出る、別の保存先へ入った場合。
- 同じサイトの複数アカウント、異なるサブドメイン、共有ログインの扱い。
- 新しい端末の追加、古い端末を使えない場合、全端末を失った場合。
- 暗号化バックアップから復元できる条件と、試験方法。
- マスター・デバイス解除・バックアップ解除・アプリ保存用フレーズの区別。
- 料金切替・退会・端末数制限で、必要な情報へアクセスできなくなる場合の退避経路。

## A2. 認証アプリの共通ステップ契約

1. すでに使う認証アプリがあるかを聞く。
2. 登録先の端末を選ぶ。設定画面を操作する端末と同じかは別に扱う。
3. 正規配布元から導入するか、既存アプリを開く。
4. アプリ自身のロック・保管庫・アカウントを必要に応じて設定する。
5. 同期を使うか、端末内だけに保つかを本人が選ぶ。
6. 同期・復元に必要なアカウントや解除情報、保護対象サービスで現在使える復旧・予備手段を先に確認する。
7. 保護対象サービスの公式画面でTOTP登録用QRまたはキーを表示する。
8. アプリ側の追加操作を、選んだ製品・OSに合わせて案内する。
9. 正しいサービス・アカウントの項目ができたことを確認する。
10. 現在のコードを、保護対象サービスの公式画面だけに入力する。
11. 公式側で登録が受け付けられたことを確認する。
12. サービス側の復旧コード等を、認証アプリの外に安全に保管する。
13. 必要ならアプリの暗号化バックアップ・同期・書き出しを設定する。
14. 既存セッションと旧端末を残して、別のログインまたは復元の確認をする。
15. 「登録できた」「予備から戻れる」の記録と、Mapのつながりを反映する。

認証アプリのインストール、アプリのロック設定、サービスのMFA有効化、同期、バックアップ、復元確認は別の状態です。1つ終わったことを理由に残りを全部完了にしません。

新しい登録を確定しないと復旧コードが発行されないサービスでは、その提供者の手順に合わせて直後に保管します。それまで現在の認証方法・ログイン済みセッションを維持し、既存方式の削除を促しません。先に利用可能な復旧方法を増やせる場合は、その設定を前提作業にします。予備がないまま強制ログアウトを伴う変更は後回しにできるようにします。

## A3. 同一端末のQR・手入力・コードの種類

QRを表示しているスマホで同じQRをカメラ撮影することを必須にしません。提供者とアプリが確認済みの手入力・同一端末連携、または別の本人の端末で表示する経路を用意します。画面キャプチャ・写真・チャットへの転送で秘密を退避させません。

次を別種類として扱います。

| 種類 | 役割・ガイドでの扱い |
| --- | --- |
| TOTP登録用のQR／設定キー | 将来のコード生成の秘密。一般のログイン承認QRと区別し、アプリへ直接登録する |
| 現在のTOTP | 短時間だけ有効な確認値。サービスの公式画面へだけ入力する |
| バックアップ／復旧コード | 端末を失った場合などの予備。使用・再生成で失効する条件を提供者別に扱う |
| エクスポート用パスワード | バックアップファイルを開くための秘密。アカウントのパスワードと同じと仮定しない |
| パスキー登録QR | 端末間のパスキー操作。TOTPアプリの追加として案内しない |
| 通知の番号照合 | 自分が始めたログインかを確認する操作。TOTPと取り違えない |

## A4. アプリ別のバックアップ・移行契約

### A4.1 Google Authenticator

同期ありと端末内だけの利用を分けます。アカウントなしのモードへ切り替える操作は、同期先からコードが取り除かれる影響を持つため、単なる表示切替として扱いません。端末内だけのコードを移す場合は、旧端末があるかを先に聞きます。[公式の同期・転送説明](https://support.google.com/accounts/answer/1066447)

Google Accountを開くためのコードが同じAccountに同期されている場合、同期だけを独立した予備手段にしません。Googleのバックアップコードや別の認証方法が、その同期なしで使えるかを確認します。

### A4.2 Microsoft Authenticator

個人用TOTP・他サービスのTOTPと、仕事／学校のアカウントやパスワードレスの登録を区別します。バックアップを復元しただけで、すべての登録がそのまま使えると説明しません。Microsoftは、仕事・学校では再サインイン・再登録が必要で、OSの種類をまたぐ復元にも制限があると説明しています。[公式復元説明](https://support.microsoft.com/en-us/authenticator/restore-account-credentials-from-microsoft-authenticator)

旧端末を残した移行と、紛失した状態からの復旧を別にします。勤務先の再登録が必要なら管理者の手順へ分岐します。

### A4.3 2FAS Auth

iOSのiCloudとAndroidのGoogle Driveの同期先を別に記録します。同一OSでの同期と、OS間の暗号化ファイル移行を分けます。バックアップファイルの解除情報は、復旧先アカウントのパスワードと同じだと仮定しません。[公式の端末間利用](https://2fas.com/support/2fas-auth-mobile-app/how-to-use-sync-more-devices-with-2fas/)

同期を有効にした後も、必要に応じて別の場所の暗号化コピーを確保します。Google Driveを開くためのコードが同じ同期の中だけにある構成を点検します。[Google Drive同期](https://2fas.com/support/2fas-auth-mobile-app/how-does-google-drive-synchronization-work/)

### A4.4 Ente Auth

オンライン同期とオフラインの利用を分けます。オフラインのコードについて、OSの移行や一般の端末バックアップだけで必ず戻るとは扱いません。暗号化エクスポート、保存先、解除用パスワード、別の信頼する環境での読み込み確認を一連の経路にします。[公式の書き出し・ローカルバックアップ](https://help-content.ente.io/help/auth/migration/export)

復旧用メールを開くコードがEnte Authの中だけにある場合も点検します。アカウントの回復キーと、書き出したファイルの解除パスワードを分けます。[循環依存の公式説明](https://help-content.ente.io/help/auth/faq/enteception/)

### A4.5 Proton Authenticator

アカウントなし、Apple側の同期、Proton Accountを使う同期の条件を分けます。Proton Mail・Passも同じAccountなら、相互に開けなくなる場合を検討します。独立した書き出し・復旧手段を先に確保します。[公式FAQ](https://proton.me/support/proton-authenticator-faqs)、[公式サポート](https://proton.me/support/authenticator)

### A4.6 Aegis

公式サイトで案内されるAndroidアプリを対象にします。保管庫解除、暗号化バックアップ、ファイルの保存先、外部へのコピー、別の環境での復元を確認するレシピが必要です。公式リポジトリと似た名称のフォークを、公式配布元として使いません。[公式サイト](https://getaegis.app/)、[公式ソース](https://github.com/beemdevelopment/aegis)

### A4.7 Bitwarden Authenticator

ローカルコード、Password Managerとの同期、OSの端末バックアップを分けます。独立したアプリだから常に保管庫と独立している、と扱いません。保管庫自身のMFAを同じ保管庫へ同期しない経路と、復旧コードの外部保管を案内します。[公式の保存先・違いの説明](https://bitwarden.com/help/bitwarden-authenticator/)

### A4.8 Authy

現行のモバイル版、電話番号の回復、バックアップの解除を別に点検します。サポートが終了したDesktop版は、新規導入先にしません。[Desktop終了の公式情報](https://help.twilio.com/articles/22771146070299-User-guide-End-of-Life-EOL-for-Twilio-Authy-Desktop-app)

アカウントへ戻れることと、暗号化されたコードを復号できることを混同しません。バックアップのパスワードを失った場合の条件と、元の端末がある場合の回復・移行を別経路にします。[バックアップパスワードの公式説明](https://help.twilio.com/articles/19753636799131-Authy-Backups-Password-Recovery)

### A4.9 組織アプリ・ハードウェア保存

Duo、Microsoftの職場アカウント、VIP等は、一般TOTPのファイル移行と同じと決めません。組織のアクティベーション・再登録・機器交換の権限を確認します。Yubico Authenticator等では、アプリ本体と、秘密を保持する物理キーを別ノードにします。アプリを再インストールしたことをキーのバックアップ完了とみなしません。

## A5. 機種変更・紛失・故障のケース

| ケース | 先に確認すること | 完了条件 |
| --- | --- | --- |
| 同一OS、旧端末あり | 既存セッション、同期先、暗号化コピー、対象アカウント一覧 | 新端末で必要なログインを確認してから旧端末の処理へ進む |
| iOS→Android / Android→iOS | 製品のOS間対応、移行形式、同期に依存しないコピー | 各対象の認証が新OSで使える。非対応は再登録手順へ分岐 |
| PC交換・ブラウザー再作成 | 保存先、拡張機能、端末認証、ローカルだけの情報 | 新プロフィールで保管庫と重要ログインを利用できる |
| 旧端末が故障 | 予備端末、復旧コード、暗号化バックアップと鍵 | 旧端末なしで復旧できる対象を確認し、残りを未完了にする |
| 端末を盗まれた | 独立したログインの確保、影響するアカウント | 既存の復旧を維持しつつ、必要な登録の失効・再登録を本人が実施できる |
| 端末も解除情報もない | 使える別経路と管理者の有無 | 復旧可能性を正確に説明し、内容削除を伴うリセットを復旧と偽らない |
| 仕事用端末・プロフィール | 組織の再登録・承認、個人データとの分離 | 許可された方法で利用を回復する |

通常の導入ガイドに、旧端末の初期化、保管庫削除、全トークン削除、既存キーの失効を含めません。それらは、新しい方法・予備手段・影響範囲を確認した後の、明示的に選ぶ別作業です。

## M1. Security Mapの依存モデル補完

### M1.1 関係の種類

- `authenticates`: 端末・認証アプリ・キーが、アカウントの認証に必要。
- `unlocks`: 端末ロック・保管庫解除方式が、保管庫や認証情報へのアクセスに必要。
- `stores`: 保管庫やアプリが、どの対象の認証情報を保持するか。秘密の値は保存しない。
- `syncs-via`: コード・パスキー・保管庫が、どのクラウドアカウントを通じて同期されるか。
- `backs-up-to`: 別のバックアップ先。単なる同期と区別する。
- `recovers-via`: アカウント等の復旧に使うメール・電話・紙・管理者。
- `requires-for-restore`: バックアップの復元に必要な解除情報やアカウントの存在。

関係を表示する前に本人の回答で確認します。製品の既定値を根拠に、今の利用者がその保存先を使っていると確定しません。

### M1.2 注意を示す条件

1. 一つの端末に全認証が集中し、独立した予備が未確認。
2. 同じ保管庫を開くコードが、その保管庫にしかない。
3. 復旧先のメールを開くための情報が、復旧させたい保管庫にしかない。
4. 同期先アカウントへ入るコードが、同じ同期に依存するアプリにしかない。
5. バックアップファイルはあるが、解除情報が同じ失う端末にしかない。
6. 予備のパスキー・キー・コードがあっても、同じ物理的紛失に巻き込まれる。
7. 復元後に組織の再登録が必要だが、その経路が未確認。
8. 同期・削除・失効によって、複数のコピーが同時に使えなくなる可能性がある。

これらは回答に基づく構造上の注意であり、侵害の発見や安全性の数値評価ではありません。「依存が循環しています」「端末なしで使える予備が未確認」など、短い理由と次の作業を示します。

### M1.3 必須の例

- Gmail→Google Authenticatorの同期→同じGoogle Account。
- iCloud→Apple「パスワード」→同じApple Account。
- Bitwarden→同じ保管庫に同期したAuthenticatorのコード。
- Proton Mail→Proton Pass / Authenticator→同じProton Account。
- Ente Auth→確認メール→そのメールのTOTPがEnte Auth内だけ。
- KeePass DB→同期ドライブ→ドライブのログインがDB内だけ。

これらの製品を使うこと自体を危険と判定しません。本人が確認した独立した予備経路があるかを調べ、その有無と未確認を区別します。

## M2. 移行・インポート・エクスポート

1. 何から何へ移すか、残すもの、対象アカウントを選ぶ。
2. 元の情報を消す前に、復旧・バックアップ・解除情報を確認する。
3. 製品が提供する移行方式を選び、秘密のファイルは公式製品間で本人が扱う。
4. このアプリはCSV・KDBX・認証トークン・QRの中身を読み込まない。
5. 平文の書き出しが必要な場合だけ、その事実・保存場所・露出を短く説明する。安全な暗号化方式がある場合はそちらを案内する。
6. 認証情報の種類ごとに移行できたか確認する。パスワード、パスキー、TOTP、添付、共有項目、履歴が同じように移ると仮定しない。
7. 同名のアカウントや重複した項目を自動的に同一視しない。
8. 新しい製品で重要なログインを実際に確認する。
9. 自動入力先・ブラウザーの保存先・端末側の既定を必要に応じて変更する。
10. 元の情報や一時ファイルの処理は、成功確認後に本人が選ぶ別作業とする。旧保管庫削除を移行完了の必須条件にしない。

移行が失敗しても、旧製品と作業記録を使って戻れるようにします。「取り消す」でサービス側のパスワードまで自動で元へ戻るとは表示しません。アプリ内の記録の取り消しと、外部設定変更の取り消しを区別します。

## T1. 追加の受け入れシナリオ

## R1. 対応表を実行可能な仕様にする

### R1.1 製品ではなく経路を公開単位にする

一つの製品を「対応」とだけ表示しません。例えば「Apple パスワード / iPhone / 既存利用 / 確認コード追加」と「Apple パスワード / Windows / 新規導入」は別の経路です。製品全体の調査済み表示で、未確認のOSへ同じ手順を割り当てません。

経路ごとに次の項目を必須にします。

| 項目 | 必須内容 |
| --- | --- |
| 識別 | 安定した製品・機能・経路・ステップID。名称変更とID変更を結び付けない |
| 適用条件 | OSの範囲、アプリ版、ブラウザー、個人／家族／仕事、地域、配布経路、必要な契約・権限 |
| 前提 | 既存セッション、復旧方法、端末ロック、管理者承認等。未確認時の分岐 |
| 入口 | 正規設定へのURL／正式な画面の開き方。深いリンクが使えないときの入口 |
| 各操作 | 開く場所、押す項目、期待する表示、本人が確認する成功条件、自然な主ボタン |
| 分岐 | 導入済み、設定済み、項目なし、QRが読めない、権限なし、契約対象外、未対応、後回し |
| 記録 | この操作で変更する回答・対策・関係・完了記録。変更しない他アカウントの範囲 |
| 復旧 | 紛失ケース、解除に必要なもの、復元できない種類、確認に使う無害な方法 |
| 根拠 | 公式資料のURL・該当箇所・閲覧日・対象条件・資料間の相違・画像の由来 |
| 翻訳 | 日本語・英語。UIの実際の表記と本文訳を混同せず、言語による項目名の違いを保持 |
| 検証 | データ整合、分岐、ブラウザー経路、実画面照合を別々に記録 |

状態は `candidate`、`researching`、`documentation-reviewed`、`implemented`、`app-flow-tested`、`device-checked`、`needs-review`、`retired`で管理します。これらはサービス側の設定完了状態と別です。未確認の手順を埋めるために、他製品のメニューや画像を転用しません。

### R1.2 全候補に要求する経路の一覧

製品に存在しない機能は `not-applicable` とし、理由と根拠を持たせます。空欄を「対応」とみなすことはできません。

| 対象 | 必須の経路 |
| --- | --- |
| マネージャー | 既存利用の確認、新規導入、正しい保存先、解除・ロック、生成・保存・更新・利用、基盤認証、独立復旧、新端末、バックアップ、復元、段階移行、削除を伴わない中止 |
| 認証アプリ | 既存利用の確認、新規導入、アプリ保護、1件の登録・利用、同一端末QR、同期の選択、暗号化退避、復元、旧端末あり／なし、OS間移行、登録不能、コード不一致 |
| 組織管理 | 本人の権限、組織による配布・承認、個人情報との分離、管理者に依頼する具体的作業、退職・端末返却前の個人用の退避 |
| ブラウザー機能 | プロフィール、端末保存／同期、解除、拡張との競合、既定の自動入力、他ブラウザー・新プロフィールでの利用、書き出しの保護 |

## R2. 調査結果を使った操作分割の具体例

以下は資料確認済みの操作を、どの粒度でレシピへ分けるかを示す仕様例です。この節を追加しただけで、アプリ実装済みとはしません。表示言語・OSで項目が異なる場合は、該当する経路の根拠を追加します。

### R2.1 iPhoneのApple「パスワード」へTOTPを追加する

前提は、対象サービスがTOTPの登録に対応し、本人が正しいアカウントの登録画面を開き、現在使える認証・復旧方法を確保していることです。Apple Accountの2ファクタ認証を、ここでTOTP登録する手順ではありません。

| 順 | その画面で行う一操作 | 次へ進む条件 |
| --- | --- | --- |
| 1 | 対象サービス側で認証アプリ登録を選ぶ | 正式なTOTP登録用QRまたは設定キーが表示された |
| 2 | 同じiPhoneか別の画面かを選ぶ | 読み取り方法を選べた |
| 3 | 同一端末では、対応するQRの長押し、またはサービス側の手入力用キーの表示へ分岐する | Appleの追加操作または手入力キーへ進めた |
| 4 | 手入力の経路では「パスワード」を開く | 本人認証して項目一覧を開けた |
| 5 | 対象サービスの保存項目を選ぶ | 別のアカウントではないことを本人が確認した |
| 6 | 編集画面から確認コードの設定を開く | 設定キーを使う画面が出た |
| 7 | 秘密の設定キーをAppleの画面へだけ入れる | 対象項目に時間で変わるコードが表示された |
| 8 | 現在のコードをサービスの公式画面で確定する | サービス側が登録を受け付けた |
| 9 | サービスの予備手段を確保する | そのコードを失っても使える方法を確認した |

英語公式画面の対応表は All / Edit / Set Up Code / Use Setup Keyです。日本語の実表示は対応する日本語資料または実機で照合してから登録します。項目がない場合は、保存項目の有無・OS・画面の違いへ分岐し、別製品の操作名を推測して表示しません。[Appleのキー入力・QR操作](https://support.apple.com/en-ca/guide/iphone/ipha6173c19f/27/ios/27)。資料確認日: 2026-11-13。

### R2.2 NordPassデスクトップで生成・保存する

| 順 | その画面で行う一操作 | 次へ進む条件 |
| --- | --- | --- |
| 1 | NordPassを開き、対象の保管庫を解除する | 正しいAccountと保管庫を開けた |
| 2 | ToolsからPassword Generatorを開く | 長さ等の生成条件が見えた |
| 3 | 対象サイトの条件に合わせ、長い固有の値を生成する | 条件に合う値が製品内にできた |
| 4 | 対象サイトで変更する前に、元のログインと新しく作った値の保存先を確保する | 失敗時に元へ戻れる状態になった |
| 5 | 公式のパスワード変更画面で本人が変更する | サービス側に成功が表示された |
| 6 | 保存項目を更新する | 対象サイト・ユーザー・保存先が一致した |
| 7 | 旧セッションを残した別のログインで利用する | 保存した情報で実際にログインできた |

コピーする場合もこのアプリへ貼り付けません。製品側の履歴と、サービス側で実際に受け付けた値のずれを解決する分岐が必要です。[公式の生成機能](https://support.nordpass.com/hc/en-us/articles/40492968030353-How-to-use-Password-Generator-in-NordPass-on-desktop-devices)。資料確認日: 2026-11-13。

### R2.3 Google Password ManagerのAndroid経路

Chromeのメニュー→設定→自動入力とパスワード→Google Password Managerを、それぞれ別ステップに分けます。新規の保存項目を追加する経路と、Webの登録・変更欄から生成候補を使う経路を分けます。Chromeの現行資料の適用条件を持ち、Androidのメーカー設定全体に同じ階層があるとは仮定しません。

表示されたGoogle Accountと保存先、対象サイト、本人のアカウントを確認します。生成・保存だけでサービス側の変更まで完了にしません。自動保存される登録経路でも、最後に保存項目と実ログインを確認します。[GoogleのAndroid向け管理手順](https://support.google.com/accounts/answer/95606?co=GENIE.Platform%3DAndroid&hl=en)。資料確認日: 2026-11-13。

## R3. パスワード・解除情報を混同させない

### R3.1 数値と生成方法

各レシピは、製品が受け付ける最低条件、対象サービスの上限・文字種、ガイドの推奨を別フィールドで持ちます。「最低値を満たす」と「この用途に十分な強さを選んだ」を同一視しません。

NIST SP 800-63B-4は中央で検証するパスワードについて、単一要素では15文字以上、MFAの一部では8文字以上を要求しています。端末の解除PIN、ローカルの保管庫暗号化、Secret Keyと組み合わせる設計へ、そのまま同じ規則を流用しません。文字種の強制や根拠のない定期変更も共通ルールにしません。[NISTの対象と要件](https://pages.nist.gov/800-63-4/sp800-63b.html)

1Passwordは固有・ランダム・覚えられるアカウントパスワードを、生成機能で作るよう案内しています。特定の文字種の混在を必須にする共通説明へ置き換えません。[1Passwordの公式説明](https://support.1password.com/strong-account-password/)

ランダム語列を案内する経路は、利用する生成機能と設定する語数まで指定します。語数を製品の公式最低条件として扱うには、その根拠が必要です。ガイド独自の余裕を持った設定なら、その旨と対象の設計を記録します。公開例、本人の名前・住所・誕生日、歌詞や思い付いた関連語を使わせません。生成機能をまだ開けない初回設定では、秘密をこのアプリへ送らずに作れる確認済みの代替方法を用意します。

### R3.2 保存先と操作上の注意

- このアプリの保存用パスフレーズ、マネージャーのマスター、提供者へのログイン、端末のPIN、認証アプリのロック、書き出し用の解除情報を、毎回の操作対象に合わせて呼び分ける。
- 生体認証を有効にしても、再起動・再認証時に必要な元の秘密を不要と説明しない。
- 紙の情報は、本人が取り出せて第三者には見られにくい場所を選ぶ。家族と共有する場合も、相手と目的を本人が選ぶ。
- 自動入力が出ないときに、似たドメインへ強制入力させない。公式のログイン先と正しい保存項目を確認する。
- クリップボード、QR、平文CSVは秘密を含み得る。このアプリが読み取り権限を要求したり、相談プロンプトへ取り込んだりしない。
- 既存の固有で適切なパスワードを保存・利用できる人には、導入確認のためだけに変更を求めない。

## R4. 認証の違い・例外・復元の確認

### R4.1 同じ保管庫にTOTPを保存する場合

他サービスのパスワードとTOTPを同じ保管庫へ保存することと、その保管庫自身を開く唯一のTOTPを閉じ込めることを分けます。前者を一律に禁止せず、利用者の選択・端末環境・独立した復旧を確認します。

技術解説では、パスワードの使い回し対策、パスワードだけの漏えい、保管庫全体が開かれた場合、リアルタイムのフィッシングで限界が異なることを説明します。TOTPがあるだけでフィッシングを防げるとは表示しません。物理キーやパスキーへの変更は、対応・予備・実ログインを確認する別の経路にします。

### R4.2 コードが合わないとき

1. 対象サービスとアカウントの項目が正しいか。
2. 登録用キー・復旧コード・現在のTOTPを取り違えていないか。
3. 端末の日時が正しいか。時刻確認はOSに合った手順で行う。
4. コードが切り替わった直後に、本人が公式画面で再試行できるか。
5. 試行制限やロックの表示があるか。無制限に再入力させない。
6. 旧方式・予備手段・管理者が使えるか。

問題の原因が確定していないまま、トークンの削除・再登録・復旧コードの再生成を解決の第一手にしません。表示された秘密やQRの共有も要求しません。TOTP生成と、クラウド同期やサービスのログインに必要な通信は別です。

### R4.3 復元テストの範囲

既存の唯一のセッションをログアウトしません。新しい信頼できる環境で試せるときだけ、既存データを上書きしない読み込み・別ログインを案内します。シークレットウインドウでは保存済みパスキーや拡張が利用できない場合も、認証情報が失われたと即断しません。

コードを消費する確認では、残りの予備・使用後の状態・再発行の影響を先に確認します。最後の復旧コードを試験で使い切ることや、成功確認のために旧端末を初期化することを要求しません。試せない場合は「保管確認」と「復元動作確認」を分けて残します。

### R4.4 終了した機能と別製品への誘導

Microsoft Authenticatorのパスワード自動入力は2025年8月中旬に終了しています。認証アプリとしての導入と、Edgeでのパスワード管理を分け、旧記事を使って終了済みの自動入力設定を案内しません。[Microsoftの公式FAQ](https://support.microsoft.com/en-us/authenticator/microsoft-authenticator-faqs)。資料確認日: 2026-11-13。

FirefoxではPrimary PasswordとMozilla Accountによる同期を別の役割として説明します。デスクトップの手順をモバイルへそのまま流用しません。[Mozillaの同期とPrimary Password](https://support.mozilla.org/en-US/kb/using-primary-password-sync)。資料確認日: 2026-11-13。
