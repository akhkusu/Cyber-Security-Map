## 2. 通常の準備と必要時の質問

新規のサービス用コードが必要になった時だけ、Ente Authと実際のスマホを選ぶ。既存MFAに再登録を強制しない。導入済みならコード・設定・同期先を保持する。正規アプリの導入／起動、画面ロック、アプリロック、現在の保存方法を別に確認する。

| 状態 | 案内 |
| --- | --- |
| 新しいアプリ・アカウントなし | 初期画面の「Use without backups」（日本語は「バックアップなしで使用する」）を選ぶ。暗号化ファイル等の独立した備えを後続で案内 |
| 新しいアプリ・既存Ente Account | 実際の既存Accountを選んでLog in。Photos等を使う人へ別Accountの新設を強制しない |
| 新しいアプリ・Ente Accountを新設 | 現在開けるメール、独立した新しいパスフレーズ・紙の控えを先に用意し、公式アプリのSign upで作成 |
| 導入済み・オフライン | 現在のモードを保持。説明のためのログインやコード移動を要求しない |
| 導入済み・同期あり | SettingsのAccountで実際のAccountを照合。同じ製品名だけで過去の確認をコピーしない |
| 自己ホスト・管理・不明な版／保存方法 | 正規の現在の利用を残し、確認できたローカル操作と、未確認の同期・復旧を分ける |

初期画面の新規登録と、既存オフラインの「Sign in to backup your codes」は別の操作。既存オフラインから同期へ変える場合は、先に現在のコードを暗号化書き出しして独立したコピーを確保する。アプリの案内に合わせるためのリセット・ログアウト・再導入をしない。

## 3. アプリのロックとコード登録

「Settings / 設定」→「Security / セキュリティ」→「App lock / アプリのロック」を開く。公式資料の古いLockscreenという呼称を、そのまま現行メニュー名へ置き換えない。既存のDevice lock・PIN・Passwordは維持できる。使えない場合、暗号化退避と本人の利用手段を確認する前に解除・再導入を案内しない。

ロックが未設定なら、実際の端末ロックを確保したうえで、対応する「Device lock / デバイスロック」を案内する。端末の本人確認が使えなければその場で別の対応方法へ分岐する。既存のPINやアプリ用Passwordから勝手に切り替えない。Auto lockの設定と閉じて開き直す確認を分け、本人が解除できた時点で記録する。

アプリロックはUIへのアクセス制限であり、Ente Accountやファイルの復旧用パスワードではない。オフラインのDBを別端末へコピーするだけでは、OSのsecure storageにある鍵を再現できるとは限らない。

コードの追加は「＋」から、別の信頼する画面のQRか、正規サービスに出た手入力用のキーを使う。手入力は「Enter details manually / 手動で詳細を入力する」で、「Issuer / 発行者」「Secret / シークレット」「Account / アカウント」を公式の指定に合わせる。指定がない限り算法・桁数・周期を変えない。本アプリへ実際のキーやコードを入力させない。

一覧への追加、サービスでのコードの受け付け、MFA有効表示、サービスの復旧情報、通常ログインを分ける。取り込み件数や同じ名前だけで実利用を済ませたと扱わない。HOTP・Steam・共有等は、専用の確認が必要なものとして一般TOTPから分ける。

## 4. Account・メール・復旧キー・追加認証

次の秘密・役割を区別し、実際の値は保存しない。

| 種類 | 役割 |
| --- | --- |
| Ente Accountのパスワード | Accountの暗号化データを開く。Photos・Auth・Lockerで同じAccountなら共通 |
| 24語のRecovery key | そのEnte Accountの復旧。提供者の予備コードやメール確認コードとは別 |
| 手動書き出し用のパスワード | その暗号化JSONを開く。Accountのパスワード変更では更新されない |
| 自動バックアップ用のパスワード | 自動・即時のローカルバックアップを開く。手動分と同じ値と推測しない |
| アプリロック・OSロック | その端末のアプリ／OSの本人確認。バックアップの代用品にしない |
| Security Mapの保存用フレーズ | このアプリの記録を開く。Enteのデータは開かない |

新しいパスワードには同梱EFFの単語表と物理サイコロで独立した6語以上を作る方法を案内し、固定した完成例を流用させない。既存の十分に強いパスワードを、説明のためだけに変更しない。紙は本人が取り出せる場所へ保管し、唯一の控えを同じスマホや同じEnte Accountの中だけに置かない。

Recovery keyは「Settings」→「Account」→「Recovery key」から、求められる本人確認を行って確保する。日本語翻訳がない項目は、配布版の英語表示と日本語の意味を併記する。24語の順序を保ち、写真やチャットに残さず、Enteやメールに入れなくても取り出せる控えを確認する。同じ実際のAccountでは共有し、各アプリで作り直さない。パスワードを変えたらキーも更新されたとは扱わない。

Ente Accountの2FAと、Authが生成する各サービスのTOTPを区別する。**Email verificationはAuthで既定OFF**であり、一般的なMFA有効化のつもりで無条件にONへ変えない。パスワード再設定では、通常ログインのこの設定とは別にメール確認が必要になる。

メールの唯一の認証が同じAuthの中にある場合、メール確認をONにすると循環することがある。先に独立したメールの予備手段と、Enteに入らず取り込める暗号化バックアップ・その解除情報、Recovery keyを確保する。別Accountを新設すれば全て解決するとも説明しない。

### パスキー

パスキーはEnteの追加認証として扱い、Accountのデータ復号をするパスワードの代わりとしない。追加すると通常の追加認証が既存TOTPに代わってパスキーへ進む影響があるため、現在のセッションとRecovery keyを先に残す。モバイルで「Login with TOTP / TOTPでログイン」が表示される場合は、本人が既存の有効なTOTPを選べる。配布版はサーバーからTOTP用のセッションが返った場合だけこの入口を表示するため、全員にあると仮定しない。TOTPで通過した操作を新しいパスキーの利用成功にしない。

1. Ente Authの「Settings」→「Security」→「Passkey」を開き、本人確認する。
2. アプリが開く正規のEnte Accountsを確認する。認証用情報を含むURLを本アプリ・AIへコピーさせない。固定した推測URLで置き換えない。
3. Ente Accountsの名前の欄に本人が見分ける呼び名を付け、「Add passkey」へ進む。
4. ブラウザー／OSで表示された実際の保存先と本人確認を使い、登録を許可する。別の保存先・不明・非対応ならその場で未完了へ分岐。
5. 今回の名前が登録一覧へ現れたことを確認する。保存先は利用者が確認した実物へ結び、未確認なら推測で端末内・同期型・物理キーとしない。
6. 既存のログインを残し、別の未ログイン環境でそのパスキーを実際に使う。その後のAccountパスワードとデータの読取りは別に確認する。

新しい登録はaccounts.ente.com。既存のaccounts.ente.ioの登録も公式アプリが該当ドメインへ誘導するため、古い登録を一括削除・再作成させない。登録だけで利用成功を作らず、新しい方法が使える前に既存方法を削除しない。

## 5. 手動の暗号化書き出し

一画面へ全部を詰めず、専用語句の用意、別の控え、正規メニュー、暗号化の選択、入力、本人確認、保存、端末外のコピーを分ける。

1. 「Settings / 設定」→「Data / データ」→「Export codes / コードをエクスポート」。
2. 「Encrypted / 暗号化済み」を選ぶ。Plain textやHTMLと混同しない。
3. ファイル用の専用語句を、Enteだけへ入力する。この画面は1つのパスワード欄であり、確認欄があると捏造しない。
4. Enteが求める端末の本人確認を行う。ロック用の欄へファイル用語句を入れない。
5. 保存の選択で暗号化JSONを本人の場所へ保存し、今回のファイルがあることを確かめる。
6. 本人が管理する別の保存先へ暗号化のままコピーし、スマホなしでファイルと解除情報を取り出せるか確認する。

配布版の手動書き出しの最低4文字は受け付け条件で、安全な推奨ではない。自動バックアップの最低8と混ぜない。既存の確認済みのファイル用語句を本人が明示して再利用できる。新規コードや再登録の後は、古いファイルを全現在データの最新コピーとして扱わない。

## 6. 自動のローカルバックアップ

手動分とは別に、必要な場合だけ「Data」→「Local backup / ローカルバックアップ」へ進む。「Automatic backups / 自動バックアップ」、専用のパスワード、保存フォルダー、実際の作成を分ける。既存の設定は維持できる。

初回の有効化では、パスワードとフォルダーの設定が先に求められることがある。既存のパスワードが保存済みなら再入力を要求しない。紙の解除情報は別途取り出せるか確かめる。新しい語句は十分にランダムなものを用い、最低8という入力制限を推奨値にしない。前後の空白が保存時に除かれることにも注意する。

iOSはFilesで保存用の**フォルダーの中**を選ぶ。「On My iPhone」の最上位を直接選べないことと、同じ場所の下に作ったフォルダーを使えないことを混同しない。Androidは本人のフォルダーを選んでOSが求めるアクセスを許可する。選択できない・権限が失われた・ドライブがない場合は、そのまま成功にしない。

「Create backup now」で今のバックアップを作り、成功表示と今回のJSONを確認する。自動分はアプリを開いた日に1回で、アプリを開かない日にも動作したとは表示しない。最大5世代の整理で古い同フォルダーのファイルが消える条件を説明する。最新の必要なコピーを別の保存先へ置くことと、本人による復元・利用確認は別の記録にする。

## 7. 新しい端末・旧端末がない場合

機種変更は通常の基本対策とは別に、実際の旧アプリ・新しい物理端末を引き継ぐ任意のガイド。旧端末なしのバックアップからの復旧を、旧アプリを操作できる直接移行と区別する。

| 状態 | 案内 |
| --- | --- |
| すでに必要なコードが新端末にある | 初期化・再取込みをせず、実際のコードを提供者で使う |
| 同じEnte Accountで同期する | 同じ実際のAccount、現在の認証・メール・復旧・パスワードを確保してログイン。OSが同じことを必要条件としない |
| 暗号化ファイルを使う | 4方向のiPhone／Androidを案内。ファイル・専用語句・実際の保存先を確認して取り込む |
| 新端末に別のAccount・固有のコードがある | その現在の利用先を残す。案内に合わせたサインアウト・Account切替を要求せず、本人の選ぶファイル追加か未完了へ分岐 |
| 旧端末を使えないが、Accountのログイン・復旧が使える | 今の本人の方法で新端末へログイン。復旧キー・メール確認・追加認証の役割を分け、読取りとコード利用を試す |
| 旧端末を使えないが、独立した暗号化ファイルがある | 新端末のオフライン利用でも取り込める。Ente Accountに入ることをファイル復元の必須条件にしない |
| ファイルだけ・語句がない／Accountも開けない | 存在だけで復旧成功にせず、使える端末・別のコピー・提供者ごとの復旧を残す |

直接のファイル転送は確認済みのAirDrop・Quick Share等の対象条件を使い、対応していないメーカーの操作名を推測しない。既に本人が保護して移したファイルからも続けられる。

取り込みは「Settings」→「Data」→「Import codes」→「Ente encrypted export / Ente 暗号化されたエクスポート」で今回の暗号化JSONを選び、そのファイル用の語句をEnteだけに入れる。通常の暗号化書き出しは生成IDを引き継がず、既存項目を一括消去する処理ではない。同じ内容は重複として省略される場合がある。未解釈の項目・件数・名前だけで全コードを使えると判断しない。

本人が対象Accountを一つずつ確認し、新端末の現在のコードを各提供者の正規ログインへ入れる。別の方法・旧コード・既存セッションで通過した場合は今回の新コードの成功にしない。確認した登録のコピーだけを同じ複製グループに結び、別方式の独立した予備と数えない。

旧端末を残す・予備・売却へ、同じ機種変更の途中位置で戻る。移行用の一時コピーと、残す暗号化バックアップを分ける。未確認の依存を残して消去へ進ませない。旧端末の後日の消去を、新端末のコード登録の失効と扱わない。

## 8. パスワード紛失・変更・削除

新しいスマホを準備するためだけにパスワードを変更しない。忘れた場合は、現在開ける本人のモバイルアプリ、取り出せるRecovery key、メール確認、別の本人のログイン、独立した暗号化ファイルを順に区別する。

モバイルの現在のセッションから変更できる場合も、新しい語句・紙の控え・必要な退避を先に確保する。Photos・Auth・Lockerを同じAccountで使う場合の影響を、必要になった時点で確認する。新しい方法の確認前に全端末サインアウトを選ばせない。新しいAccount認証と既存データの読取りを確認した後も、以前のエクスポート用語句が変わったとは扱わない。

全端末からログアウトした状態のパスワード再設定では、メールの確認とそのAccountの24語のRecovery keyを使い、新しいパスワードを設定する。追加認証を要求される場合は、その確認・復旧も別に行う。現在の公式資料と配布タグのサーバー実装を照合した結果、パスキーとTOTPの復旧を「いずれも登録解除」としていた初版の説明を訂正する。

- パスキーの「Recover two-factor」は、そのログインでのパスキー確認を迂回する。登録済みパスキーの削除ではない。紛失した鍵の登録解除は、使える代替手段を確認してから別に行う。
- TOTPの「Lost two-factor device / 紛失した二要素デバイス」から復旧キーを使う操作は、この同じEnte AccountのTOTPを無効にする。同じAccountで使うPhotos・Auth・Lockerに影響するが、Authが保存するほかのサイトのコードの無効化ではない。
- どちらも、Accountパスワードで既存データを読めるかの確認は別に必要。復旧後の保護と独立した復旧手段を確保する。

根拠は[公式のパスキー復旧](https://ente.com/help/photos/features/account/passkeys)と、配布タグの[パスキー認証の迂回](https://github.com/ente/ente/blob/9684542adf1881515c49a60685cbf53423223e63/server/pkg/controller/user/passkey.go)、[TOTP復旧](https://github.com/ente/ente/blob/9684542adf1881515c49a60685cbf53423223e63/server/pkg/controller/user/twofactor.go)、[ログイン発行時の無効化条件](https://github.com/ente/ente/blob/9684542adf1881515c49a60685cbf53423223e63/server/pkg/repo/userauth.go)。2026-11-14に確認した。再設定の途中でエラーが出ても変更が反映済みの場合があるため、唯一のセッションを閉じたり、同じ物理変更をむやみに繰り返したりしない。

復旧キーの露出は、通常のパスワード変更だけで解消したと記録しない。Accountの削除・作り直しはAuthだけのリセットではなく、同じAccountのPhotos・Locker・契約・家族にも影響する。必要な退避と本人の計画を確かめる前に、削除を一般的な復旧として案内しない。削除後の復旧期間・条件と、通常の失念からの復旧は分ける。

### 8.1 現在開けるモバイルからの変更・失念

入口は、Security Mapの実際のEnte Authアプリにある「このAccountの失念・変更・復旧を進める」。Account保護中の「取り出せない・忘れた」からも、同じAccountの復旧の子ガイドへ進む。

| 一画面の操作・質問 | 開く場所・本人が確認する結果 |
| --- | --- |
| 今回の目的 | 失念、変更、追加認証が使えない、現在の方法の確認を区別。確認だけの人へ変更を要求しない |
| 進める場所 | 同じAccountが開くモバイルを保つか、使える実端末のWebを使うか。紛失端末を選択だけで利用可能に戻さない |
| 現在のAccount | Settings → Accountで同じAccountか照合し、現在のコード・使えるログインを残す |
| 独立バックアップ | 不足する場合だけ暗号化バックアップの子ガイドへ。既存の確認を一律に消さず、同じ復旧へ戻る |
| 同じPhotos・Locker | 実際の同じAccountの利用だけを確認。別Accountの進捗・パスワードは変更しない |
| 復旧キーを開く | Settings → Account → Recovery key。端末の本人確認後に、今回のAccountの24語を確認 |
| キーを保管する | 正しい語と順序を照合し、Ente・スマホなしで取り出せる紙の控えを残す。ここへ値を入力させない |
| 新しい語句を用意 | EFFの7776語表を同梱。サイコロ5回で1語、独立に6語以上。本人が意味で選んだ語・完成例を使わせない |
| 新しい控えを保管 | 同じ実物の紙か、別の実物かを選べる。候補を控えただけでは現在のパスワード・構成世代を変更しない |
| 変更画面を開く | Settings → Account → Change password。モバイルの開いているログインと端末の本人確認を使う。古いパスワードを要求する別のWeb経路と混ぜない |
| 新しい値を入力 | 新しい値とConfirm passwordの2欄へ、Enteだけで入力する |
| 変更を送信 | Change passwordで出るサインアウトの選択ではDo not sign out / サインアウトしないを選ぶ。今回の変更を一度送信 |
| 結果を確認 | 成功した場合は一回の回答で実際の変更を記録。不明・エラーなら送信を繰り返さず、同じ候補の確認へ |
| 新しい値を試す | 既存ログインを保った別のプライベート画面で、控えの新しい値そのものを使う。自動入力の古い値・既存セッションで代用しない。追加認証の画面は開いたまま、次のAccount確認で一操作ずつ進める |
| 現在の保護を確認 | 同じAccountの既存の追加認証、または新設した代替手段を正規ログインで試し、データ読取りを確認する |

Security Mapは送信結果が未確認なら「復旧の結果を確認」、途中の作業なら再開が必要な状態を示し、ノードと詳細に同じ結果を表示する。未確認の送信を後回し・中止にしても結果確認を消さない。

変更の送信後は、古いパスワードによる過去のログイン・復号の確認を、現在の利用可能性として使わない。新しい値が実際に受け付けられれば、不明だった同じ変更を確定する。二度の変更として記録しない。取り消し・後回し・再開は実際のパスワード変更を戻さず、さらに後の変更を古い候補で上書きしない。24語キー・過去の暗号化書き出し・その解除語句・他サイトのTOTPは維持する。

### 8.2 旧端末なしのWeb復旧と、新しいスマホでの保護

Webで使う実端末はiPhone・Android・Mac・Windows・Linuxから、必要になった時点で確認する。ブラウザーの入口は確認済みの正規Auth Webで、未確認の再設定用URLや一時トークンを組み立てない。

1. 正しいメールを独立した手段で開けること、今回のAccountの24語キーを取り出せることを確認する。
2. 別のプライベート画面で正規Auth Webを開き、Loginで今回の既存Accountを選ぶ。新しいAccountを代用しない。
3. 実際に出た「パスワード欄」「メール確認コード欄」「別の画面」を選ぶ。通常のEmail verificationがOFFなら、ログインのたびに必ずメール確認されるとは案内しない。
4. パスワード失念ではForgot password、今回のメール確認を経て、表示された追加認証・復旧キー欄へ進む。現在使える追加認証は変更しない。
5. パスキー・TOTPを使えない場合だけ、それぞれの復旧を選ぶ。方式ごとの上記の影響を示してから、Enteだけへキーを入力しRecoverする。送信後に記録を取り消しても再送信へ戻さない。
6. パスワード再設定では、このAccountの24語キー、新しい値の2欄、Change passwordを一操作ずつ案内する。現在の値を保つ追加認証の復旧とは分ける。
7. 新しいログインで実際に使った追加認証を確認し、既存コード一覧を読めたことを記録する。紛失したスマホだけにある認証手段を候補にしない。復旧キーでの通過をMFAの再設定成功にしない。
8. 追加認証を復旧した場合は、使えるモバイルアプリで同じAccountを開き、現在の追加認証・データ読取りを確認する。Webに使ったMac等と、その後に使う新しいスマホを別の実端末として保持する。
9. 新しいモバイルが未記録なら、正規アプリの導入・版・実際の状態・同じAccountへのログイン・保存・ロックの子ガイドへ進む。別Account・オフラインの固有コードがある場合は保留し、削除・切替・代わりの新設を要求しない。
10. 新しい方法の実利用とデータ読取りが確認できた後、同じ復旧・元の作業へ戻る。旧端末を使わずに試した範囲だけを記録する。端末が失われた事実や、別Accountの状態は変えない。

TOTPの無効化の送信結果が不明な間は、そのAccountの過去のTOTP利用確認を現在の成功として再利用しない。送信済みの方式を「戻る」で別方式へ置き換えない。「復旧キー」と「まだ記録していない別の方法」は別回答とし、不明な方式をキーの利用・MFA成功へ推測で変換しない。

現時点の入口は、同じAccountとの接続を記録済みのアプリからの復旧である。すべてを初めて登録し、接続履歴もない状態からの復旧、紛失パスキーの個別登録の削除、復旧キー露出後の作り直しは、追加の専用経路が必要。パスキー迂回だけで紛失した登録まで削除済みとは表示しない。

### 8.3 保存と例外時の補助

`recoveryStateV1`は秘密の値ではなく、今回の候補のID・送信／適用の状態・日時・構成世代を保持する任意項目。従来の暗号化保存・バックアップ内に保存し、未知項目を維持する。型・所有Accountが不正な既知項目は上書きせず、保護対象とする。作業IDをAccount・端末・親ガイドへ結び、異なる補助ガイドへ完了を流用しない。

通常の説明はこのアプリ内に置く。画面違いなどのその場の案内で解決しない場合だけ、実際の操作端末のOS、現在の一操作、期待表示、選んだ困りごと、公式出典を含む相談文を手動コピーできる。クリップボードを利用できない場合は、読取り専用の相談文を選択してコピーできる。呼び名・実メール・秘密・自由入力・一時URLを含めず、自動送信しない。

## 9. 記録・Security Map・進行

実際のAccount、メール、端末、アプリ、端末内データ、Accountの同期データ、値を持たない認証情報、復旧キーの控え、物理ファイルと各コピーを別IDで管理する。共有する同じAccountの確認は再利用し、別のAccount・端末・保存先へ完了をコピーしない。

元ファイル・外部の恒久コピー・新端末の一時コピーは同じ内容のグループへ結んだ別の実体。保存・復元元の過去の由来は、現在のコード生成へ毎回必要な依存と分ける。紙や保存先が使えなくなれば、バックアップの再確認が必要な理由を示す。

アプリロック、Accountの認証、暗号化データの読取り、TOTPの追加認証、ファイルの保管、復元を別の観測にする。通常利用を全端末喪失後へ広げない。実際のAccountパスワード変更では古い認証・復号の確認を使わず、無関係なサービスのTOTPを全部やり直した扱いにしない。登録の失効は同じ秘密のコピーにも反映する。

戻る・後回し・暗号化再開・記録の取り消しを備え、最後の実操作のボタン1回で記録と移動を終える。過去の操作へ戻っただけなら、保存した有効な確認で続けられる。取り消すのは記録であり、実際のパスワード・ファイル・接続・削除が元に戻ったと表示しない。

必要時だけ新しい版付きデータを追加し、旧1〜11の未知項目、ID・全進行・暗号化封筒v1とバックアップを保持する。同名の不明な項目を上書きしない。説明の更新だけで確認を消さず、実際の構成・秘密の変更、登録の失効、確認の訂正を区別する。

## 10. 例外と相談

画面違い、項目がない、非対応・権限、ロック・解除情報が使えない、同期されない、取り込みの失敗、違う認証方式で通過した場合を、その操作から選ぶ。内蔵の分岐を先に使い、未解決の場合だけ、サービス・OS・適用版・一操作・期待表示・困りごと・公式の根拠を手動コピーする。

実際のメール、パスワード、キー、QR、コード、Accountへの一時URL・トークンを相談文へ含めない。画像を添付する場合も隠すよう案内する。AIに最新の公式情報の確認と、一度に一つの質問／操作を指示し、確認できない場合は明示させる。外部AIへ自動送信しない。

### 記録を分ける条件

- アプリの選択・準備・バックアップ保管だけで、対象サービスのMFA・ログイン・復元を完了にしない。
- 同じコピーしかないと本人が確認した場合は、既存の暗号化ファイルに対して移行先の現在のコード一覧のカバー範囲を記録できる。同じファイルの物理IDを複製しない。新規・変更・固有コードがあれば移行先を新しくバックアップする。未登録の古い書き出しは、取り込めたという理由だけで「現在の全コードのバックアップ」にしない。
- 新端末でTOTPを使ってログインできた確認は、任意の機種変更の同じAccountのログイン確認へ反映する。暗号化保管庫を読めた確認は別であり、省略しない。全端末喪失後の成功とも扱わない。
- 移行先のAccountを確認する子ガイドでは、旧端末を使わずにその端末で試す指示を明示する。実際の認証手段が旧端末だけにある場合は止める。通常のAccount確認を、旧端末なしの成功へ広げない。
- 子ガイドは実際の親作業・作成時点・端末ペアへ結び付ける。別の親の未完了作業へ合流せず、取り消した子確認は機種変更の記録・消去前の判断にも反映する。秘密や実ファイルは保存しない。
- revision12の旧記録と未知項目・既存の暗号化封筒・バックアップを保持する。新しい復帰・ファイルのカバー範囲は専用の付随情報で管理し、不明・壊れた情報から成功を作らない。
