# Bitwarden・1Passwordのアカウント・保管庫・変更手順

調査・契約日: 2026-11-14。これは実装対象の契約です。現在の実装をすべて満たしたという意味ではありません。実装状況・試験対象SHAと分けて管理します。

既存の製品別仕様P2・P8、主要プラットフォームのBW01〜BW11、機種変更の契約を具体化します。対象は新規導入だけではなく、既存の強いマスターを維持する人、弱いマスターを変更する人、複数アカウント、複数端末、保管庫・認証・復旧の違いを含みます。

## 1. 利用者への質問と名前

- 最初からアカウント、保管庫、端末、OSを一括登録させない。今の操作で必要な情報だけを聞く。
- 登録がない初回に「登録済みの項目を使いますか？」を出さない。同じ製品に本人の記録がある場合は、呼び名・任意のメール・用途で選べるようにする。
- 同じ製品でも個人用、仕事・学校用、別メール、別サーバーは別のアカウントとして扱う。アドレスの一致だけでも統合しない。
- メールと呼び名は任意で暗号化保存する。実際のマスター、Secret Key、認証コード、復旧コード、設定用QRを入力する欄は作らない。
- メールの入力は識別のため。復旧先のメールや別のAccountとの関係は、実際の相手を本人が確認した時だけ追加する。
- 表示では「このBitwardenアカウント」「選んだ保管庫」「この端末」を使い、内部用語のRoot、基盤、スコープを操作文へ出さない。

## 2. 区別して記録する対象

| 対象 | 識別と確認 | 共有してはいけないもの |
| --- | --- | --- |
| アカウント | 既存Asset ID、製品、本人が確認した提供先、用途、任意の呼び名・メール | 別サーバー・別AccountのMFA、復旧、マスター |
| 保管庫 | ランダムなID、所属Account、私用／共有・管理対象、本人が区別できる名前 | 同じAccount内でも別Vaultの保存項目・共有範囲 |
| アプリの利用場所 | 端末ID、Web／アプリ／拡張、利用Account、必要なプロフィール、参照する保管庫 | 別端末の開封、自動入力、実ログイン |
| マスター等の情報 | 対象Account・Vault、用途、値を使えた記録と変更時点 | パスワード、Secret Key、MFA、PINを一つの万能な鍵として扱うこと |
| 緊急情報・控え | 何の情報の控えか、本人が区別する保管先、対象の変更時点、読めた確認 | 同じ紙に保管した複数の秘密を独立した予備と数えること |
| 作業 | 対象ID、手順ID、候補・変更の試行、受け付けた結果、確認日、根拠 | 古い成功を、後の変更や別の対象の完了へ使い回すこと |

旧Assetを新しいAccountへ勝手に置き換えない。既存ID・参照・進捗・未知項目を維持し、必要なVaultと利用場所の記録を追加する。過去の全体的な確認から、複数端末それぞれの成功を作らない。物理的に同じアプリから二つのVaultを開く場合も、二台の独立端末とは数えない。

## 3. サーバー・ログイン先

### 3.1 Bitwarden

米国とEUのAccountは分離されており、地域の表示を切り替えても既存データが移るわけではありません。[公式: サーバーの選択](https://bitwarden.com/help/choose-my-server/)

1. 既存のWeb版なら、現在利用しているアドレスのホストを読む。米国のvault.bitwarden.comとEUのvault.bitwarden.euを区別する。
2. すでにログイン中のモバイル版では、上部の丸いAccountアイコンで一覧を開く。選択中のメールの下に表示された提供先を読む。公式資料のiPhone例にはvault.bitwarden.com、Android例にはbitwarden.comが表示されている。位置や表記が違う場合に備え、OS別の目印と例外を用意する。[公式本文・図](https://bitwarden.com/help/account-switching/)
3. ログイン／登録画面では、ServerまたはLogging in onの選択を確認する。現在のAccountを調べるためにサインアウトさせない。追加Account画面の初期選択を、別の既存Accountの提供先と推測しない。
4. 本人が確認するまで米国のURLを既定値として開かない。旧データの途中位置、Mapからの起動、前提手順からの復帰も同じ判定にする。
5. セルフホストは別の選択肢とし、本人が確認した接続先と公式Bitwardenの構成を扱う。URL中の認証情報・トークン・クエリーは記録しない。未確認のホストや設定URLを作らない。互換サーバーは公式Bitwardenと同じ確認済み実装として扱わない。

新規Accountは、選んだ公式登録先と、登録に成功したAccountを区別して記録する。別サーバーを選び直した場合は、旧Accountの記録を残して別のAccountへ進む。選び間違いの訂正と、別Accountへの切り替えをその場で区別し、既存の対策を無条件に引き継がない。

### 3.2 1Password

個人用のログイン先にはmy.1password.com・my.1password.ca・my.1password.euがあり、家族・チーム等には固有のログイン先があります。普段使うログイン先またはEmergency Kitで確認します。地域の移行は別Accountへの移行として扱います。[ログイン先の確認](https://support.1password.com/sign-in-troubleshooting/) / [地域](https://support.1password.com/regions/)

- start.1password.comは公式の入口として使えても、本人の実際のAccount・地域・Vaultを確認済みにする根拠にはしない。
- Secret Key・パスワード・QRそのものを本アプリへ転記しない。ログイン先を見つけられない場合は、公式画面のAccount検索をアプリ内で案内する。
- 個人・家族、チーム・仕事、SSO、パスワードレス、旧ローカル保管庫を同じマスター作成の手順へ流さない。必要な分岐は、その情報が必要になった時に聞く。

## 4. 既存のマスターを維持する経路

1. 正しいAccountを選び、既存の保管庫を開けるか確認する。
2. そのAccount専用でランダムに作った十分に強いマスターは維持できる。定期変更や「新しい方が安全」という理由だけで変更させない。
3. 生体認証・PIN・開いたままの保管庫だけで、現在のマスターを使えたと記録しない。
4. 強いマスターを維持する経路でも、必要な緊急情報、マネージャー自体のMFA、重要な保存項目の利用へつなぐ。これらを一つの確認へまとめない。

仕組みの解説では、ランダムな固有の値が使い回し攻撃・推測に有効な理由、暗号化されたデータが盗まれた場合の推測、開いた端末やマルウェアに対する限界を説明する。注意書きの反復で代用しない。

## 5. 弱い既存マスターの変更

### 5.1 変更前の備え

一画面に以下をまとめず、必要な操作ごとに分ける。

| 操作 | 次へ進める状態 | 進めない場合 |
| --- | --- | --- |
| 現在のマスターの控えを取り出す | どのAccountの現在値か分かり、独立した控えから読める | 不明なまま変更画面へ進まず、現在使えるアプリを残して復旧分岐へ |
| 製品の緊急情報を用意する | Bitwardenの提供先・登録メール・利用可能な認証、1PasswordのEmergency Kit等を確認 | 既存の情報を削除せず、必要な取得手順へ |
| 登録メールの利用を確認する | 新しいログイン等で必要な受信を、そのAccountのメールで行える | マネージャーの中だけにあるメールの認証情報へ循環依存しないよう、先に整える |
| 新しいフレーズを用意する | 製品の条件を満たす専用のランダムな値 | よく知る文章・例示された値・本アプリ保存用のフレーズを流用しない |
| 候補を紙へ控える | 現在値と変更予定の値を区別し、施錠して保管できる | 私有で保管できなければ後回し |
| 控えを読み直す | 変更フォーム・マネージャーを閉じても同じ候補を取り出せる | 読めない・一致しない状態で確定しない |

長さの具体値とランダムな単語を選ぶ方法は、製品の一次資料とEFF等の元の方式に結び付ける。単語を本人の好みで選ぶ方法とは区別する。1Passwordは専用・ランダム・覚えられる値を勧め、保管のためのEmergency Kitも案内しています。[公式](https://support.1password.com/strong-account-password/)

### 5.2 BitwardenのWebでの変更

| 安定した操作IDの例 | 行うこと | 確認すること |
| --- | --- | --- |
| master-settings | 正しい提供先のWeb版でSettingsからSecurityへ進む | 対象Accountの設定 |
| master-tab | Master passwordのタブを開く | 現在値と新しい値の入力欄 |
| master-current | 現在の値をBitwarden側へ入力する | 入力先は正規のBitwarden |
| master-new | 紙から読み直した候補を、新しい値と確認欄へ入力する | 同じ候補を入力できる |
| master-submit | Change master passwordで確定する | 成功した結果・自動ログアウト、または拒否・不明 |
| master-result | 実際の結果を一回の回答で記録する | 記録しただけで未実施を成功にしない |

基本経路に暗号鍵の変更を混ぜません。Webは変更後に自動ログアウトするため「変更後もこのWebのログインを残せる」と約束しません。候補と必要な情報を先に取り出せる状態にします。[公式手順](https://bitwarden.com/help/master-password/)

### 5.3 1PasswordのWebでの変更

正しいAccountへ入り、名前からManage Accountを開き、Change Passwordへ進みます。入力、確認、確定、受け付けた結果を個別の操作にします。変更後はEmergency Kitも新しい値に合わせます。[公式手順](https://support.1password.com/change-account-password/)

旧1Password 7 for Windowsに必要な再認証は現行アプリと分けます。SSOやパスキーで利用するAccountに、存在しないマスターを作らせません。別の認証方式を選ぶだけで、現在のものを削除しません。

### 5.4 変更後

1. 正規サービスが受け付けた結果を記録する。拒否・不明では成功にしない。
2. 新しい値を、独立した恒久的な控えへ反映する。候補の紙を使う場合は「現在使用中」と分かるようにする。
3. 1Passwordは必要なEmergency Kitを取得し、新しいAccountパスワードを記入して保管する。Secret Keyや復旧コード等を同じものとして扱わない。[Emergency Kit](https://support.1password.com/emergency-kit/)
4. 正しい提供先・Accountで新しいログインを行い、マスターで保管庫を開けるか確認する。旧パスワード・PIN・生体認証・既存セッションだけの利用を、新しい値の成功にしない。
5. 既存のMFAを求められた場合も使えるか確認する。表示されたコードを見ただけで成功にしない。使えると確認する前に既存の方式を削除しない。
6. 保存項目と必要な緊急情報を残す。不要であると区別できる一時控えだけを整理する。空の保管庫への置換・全消去・Accountの作り直しを通常の確認方法にしない。

## 6. 1Passwordの復旧コード

個人・家族Accountでは、WebでAccount管理を開いてコードの準備へ進める。取得、保管、読み出し、登録メールへのアクセスを分けて確認する。コードを用意しただけで復旧を実行しない。最近のログインによる待機があるため、基本設定の試験として即座にAccountを復旧させない。[公式](https://support.1password.com/recovery-codes/)

コードによる復旧ではメールへのアクセス、新しいSecret Key、新しいAccountパスワード、各端末での再ログインを扱う。MFAが維持されることと、コード自体が後でも使えることを、現在の公式条件に沿って扱う。家族管理者による復旧や仕事用の復旧と混ぜない。コードの取り替え・無効化も、それぞれのコピーへ反映する。

Bitwardenの二段階認証用コードを、マスターを忘れた時の万能な復旧手段として説明しない。1PasswordのEmergency Kit、Account復旧、MFAの予備も役割を区別する。

## 7. 保存候補・再開・互換性

- 保存候補、変更の受け付け、控えの更新、実利用を別記録にする。各記録を実際のAccount・提供先・Vault・利用場所・試行・既知の変更時点に結び付ける。
- 説明の修正だけで完了を消さない。新しいマスターの受け付けだけでMFA・自動入力・他サービスでの実利用をまとめて完了にしない。
- 変更後に閉じた場合は、残っている作業から再開する。戻る操作から新しい変更を繰り返させない。誤った受け付け記録を取り消しても、実際のパスワードを元へ戻したことにしない。
- 変更前の成功記録は履歴として残し、変更後の進捗・現在の利用可能性には使い回さない。別端末の成功を、その端末での利用と推測しない。
- 旧データでサーバーや端末が未指定なら、その情報だけを必要時に補う。AccountのMFA・復旧等を一律にやり直させない。曖昧な保存候補は安全に再確認し、確定前に使えると確認する。
- 既存の暗号化封筒・バックアップ形式・安定した手順ID・未知項目を保持する。読めない将来形式は上書きせず、原本の書き出しと対応版での再開へ案内する。

## 8. Security Mapと機種変更

| 観測 | Mapの意味 | そこから保証しないこと |
| --- | --- | --- |
| 提供先とAccountを選んだ | 使うAccountの記録 | ログイン成功・MFA有効化 |
| 私用のVaultを選んだ | 本人が確認した保存対象 | 他のVaultや共有項目の完了 |
| アプリで開いた | この端末のこの利用場所で開けた | 新しい端末での認証・マスターによる解除 |
| 独立した控えを読んだ | このAccountの現在の控えを取り出せた | 実際のAccount復旧・複数の物理コピー |
| 新しいマスターで開いた | この変更時点・利用場所で実際に開けた | 全端末・全保存項目の確認 |
| サービスで保存パスワードを使った | このAccount・保存先・端末で実利用した | 別のサービス・別Accountの完了 |

新しいスマホでは、アプリの導入、正しい提供先・Account、実際のVault、現在の解除情報、既存MFA、重要な保存ログインを確認する。主ガイドの途中位置をPhoneから書き換えない。独立した控えの同じ確認は共有し、端末ごとの利用は個別にする。

旧端末を残す、予備にする、売る場合を区別し、消去・譲渡の前に未完了の引き継ぎ・認証・復旧を確認する。別端末でログインできただけで、控えがAccountから独立していると推測しない。

| SM22 | 変更前の成功を現在の完了・進捗へ流用しない |
| SM23 | Account復旧とMFAの予備を製品固有に区別する |
| SM24 | コードの準備を、復旧の実行・成功と扱わない |
| SM25 | 登録メールの確認と、関係の追加を本人の回答に結び付ける |

| SM28 | 保存した重要なパスワードを実際に使うまでつなぐ |
| SM29 | 一つの確認・取り消しをガイド・進捗・Mapへ同じ意味で反映する |
| SM30 | 新端末の利用と、既存端末・独立した控えを区別する |
| SM31 | 未完了の移行がある場合は消去・譲渡を進めない |
| SM32 | 旧データに足りない情報だけを補い、再登録を強要しない |
| SM33 | 暗号化再開、未知項目、保存失敗、日英・390px・キーボードを確認する |
| SM34 | DockerのみとGitHub Pages配下で同じ手順・記録を使える |

実装はAccountと提供先の識別、Vaultと利用場所、変更前の備え、製品別変更、変更後の実利用と控え、Map・Phoneの順に接続する。各段階の確認と、全条件の完了を混同しない。

## 10. 資料と画像の扱い

上記リンクの公式本文を2026-11-14に確認しました。BitwardenのモバイルAccount一覧は、公式資料の画像を調査用として目視し、本文だけで未確認の位置を推測していません。この画像はアプリへ取り込んでいません。再配布条件を確認していない資料画像を、製品の説明画像として同梱しません。

手順データには資料ID・URL・対象クライアント・OS・最終確認日・確認方法を持たせます。実Accountでの設定・復旧を行ったという意味ではありません。画面が違う場合はその場の分岐で扱い、未確認の項目名や設定URLを生成しません。


## 実装追補: Bitwardenのサーバー確認（2026-11-14）

この追補はSM契約のうち、サーバーの取り違えと既存記録の保持に対応する実装です。Account・Vault・利用場所の型付き管理、任意の識別用メール、1Passwordの提供先、既存の弱いマスターの実変更など、SM01〜34全体の完了は意味しません。

- 未回答・不明・セルフホストをUSと扱う既定値を、レシピ・ブラウザー補助・保存候補の識別から除きます。アプリの導入やフレーズ準備の段階には不要な質問を追加せず、実際にサーバーが必要な操作で聞きます。
- Web画面のホスト、iPhone／iPad・Androidのアカウント一覧、ログイン画面のServer／Logging in onを、表示場所に合う一操作として案内します。現在のアカウントを調べるためにログアウトさせず、Add Accountの初期値を既存アカウントの根拠にしません。説明・表示条件・資料確認日は`bitwardenServerCatalog.ts`、回答の処理は`bitwardenServer.ts`、画面は`BitwardenServerCheck.tsx`へ分離します。
