# Google・Apple・BitwardenとSecurity Mapモデルの再監査

版: 1.0 / 公式資料の調査・コード照合日: 2026-11-13

この文書は[全体仕様](PRODUCT-SPEC.md)と[製品別補完仕様](PASSWORDS-AUTHENTICATORS-SPEC.md)への必須追補です。既存の70シナリオに、主要3系統の経路58件、モデル20件、削除・失効12件を追加します。これは受け入れ条件の定義であり、160件の自動テストが通ったという意味ではありません。

## 1. 再監査の結論と調査の境界

前版は主要製品の名前・MFA・復旧の共通経路を扱っていますが、仕様を確定するには不足がありました。特に次の設計を補います。

- 認証、復号、ローカル解除、既存セッション、外部アプリへの権限を別にする。
- 物理端末と、その上のブラウザープロフィール・アプリのインストール・認証情報を別にする。
- 識別子とアカウントを分ける。別名メール、電話番号、組織ID、ドメインを扱う。
- 「一つあればよい予備」と「全部が必要な復旧条件」、待機期間、組織の権限を表現する。
- Google・Appleの基盤Account、Bitwardenの保管庫へのアクセス条件を製品固有にする。
- 記録の削除、認証の失効、秘密のローカル削除、サービス・Accountの削除を分ける。
- 古い完了記録と、現在も利用できることを別に記録する。

調査では、公式の認証・復旧・パスキー・バックアップ・共有・紛失・削除資料と、現在の `src/models.ts`、ガイド状態・関係のモデルを照合しました。本文を確認した資料と、取得制限により公式検索抜粋で確認した資料は、末尾の出典表で区別します。実機で未確認の項目名・画面・OS条件を確定済みレシピとして公開しません。

「考えられる全世界の製品・全将来版・全組合せを確認済み」とは扱いません。網羅性は、この文書の対象の種類、ライフサイクル、主要3系統の条件分岐、障害シナリオ、移行・削除の影響を対応表で追跡できることによって確認します。

## 2. コード照合で確認した到達モデルとの差

| 監査時の構造 | 表現できない、または曖昧になること | 必要な変更 |
| --- | --- | --- |
| `AssetKind`はdevice / account / backup / network / identity | 物理キー、認証情報、ソフトウェアの利用場所、権限、連絡先の役割が混ざる | 安定した拡張種別と、下記の論理的エンティティを追加 |
| `provider`と`services`は限定された列挙 | 新しい製品・基盤ID・サーバー・サービスの追加がUIと保存形式に波及 | 表示名から独立した製品・機能レジストリと適用条件を使う |
| 同じ対象に`mfa`という一つの対策値 | TOTP、FIDO、パスキー、復旧コード、組織認証の違いが消える | 登録方式ごとの状態と、基盤認証ポリシーを保持 |
| 4種類の関係 | 所有、保存、同期、ローカル解除、権限付与、SSO、復号条件が表せない | 型を持つ関係・権限・条件付きアクセス経路を追加 |
| 二項関係をたどる依存表示 | 代替手段と同時に必要な条件を区別できない | ALL / ANYと条件・待機を持つアクセス経路を追加 |
| `verified`等の完了状態 | 過去の実施と、紛失・失効後の利用可否が混同される | 作業履歴、現在の可用性、根拠、確認日時を分ける |
| 自由な`type`・`notes` | 種類が同じ文字列という理由で誤集計し、秘密を混ぜる恐れ | 種別は構造化し、呼び名だけを利用者が付ける。秘密は収集しない |
| Zodが未定義キーを除去する設計 | 新形式や旧ソフトウェア情報を読み書きしただけで失う恐れ | 移行前原本、既知形式の明示的移行、未知の利用者データの保持・読み取り専用分岐 |
| Mapで項目と関係を削除 | 現実の失効や他の予備への影響までは確認できない | 記録削除と実際の設定変更を分け、関連する未確認事項を残す |

上記のうち、保存時の未知項目の保持・未対応形式の拒否・原本退避は修正を実装しました。その他の到達モデルは未実装です。詳しい検証範囲は[実装状況](IMPLEMENTATION-STATUS.md)で分けて管理します。

### 3.2 エンティティの識別と最小データ

共通のIDはランダムに生成し、実際のメール・電話・デバイス識別番号をキーにしません。`entityType`、`productId`、`scopeId`、所有・管理区分、呼び名、作成・更新時刻を持ちます。`scopeId`で、個人／家族／仕事、サーバー、テナント、プロフィールを区別します。

認証情報には、`credentialType`、`subjectAccountId`、`storageRef`、`replicaGroupId`、役割（sign-in / second-step / decrypt / local-unlock）を持ちます。同じ物理キーを二つのAccountへ登録しても、登録記録は別です。同じパスキーの同期コピーを、二つの独立した認証方式と数えません。

Identifier、Principal、Service、Credential、Installation、DataSet、Grant、RecoveryArrangementを論理的に分けます。表示上は必要に応じてまとめても、本人が同じ認証主体だと確認しない限り統合しません。ドメイン名や公開鍵も個人を推測できる場合があるため、値の収集を必須にしません。

## 4. 関係・アクセス条件・紛失の意味

### 4.1 関係の契約

| 種類 | 向きと意味 | 区別するもの |
| --- | --- | --- |
| owns / administers | 人・組織→対象 | 所有と管理・利用の権限 |
| installed-on | アプリ／プロフィール→端末・環境 | 製品と利用場所 |
| identifies / alias-of | 識別子→認証主体 | 別名メールと別Account |
| authenticates-to | 認証情報／IdP→Account | サインインと復号 |
| unlocks / decrypts | 解除手段→保管庫・データ | ローカル解除とサーバー認証 |
| stored-in / synced-via | 認証情報・データ→保存先・同期基盤 | 同じ情報の複製と別の予備 |
| session-for | セッション→Accountと利用環境 | 物理端末と認証済み状態 |
| grants-access-to | 権限→対象データ・Account | ログイン連携と読み書き権限 |
| delegated-to / shared-with | 対象→相手・共有範囲 | 復旧連絡先と通常アクセス |
| recovers / requires-for-restore | 復旧経路→対象・必要条件 | 復旧の資格と実際の動作条件 |
| backs-up / restores-from | バックアップ集合→元データ／復元先 | 同期と履歴を持つコピー |
| hosts / routes / manages-domain | サービス基盤間の役割 | DNS・メール・ホスト・キャリア |
| invalidates / replaces | 変更・新しい登録→影響対象 | 新規設定、ローテーション、失効 |

全関係に、確認主体、確認日時、根拠、適用条件、状態を持たせます。製品の既定動作を、本人が現在利用している関係として自動確定しません。図の矢印の向きと文章表示は一貫させ、旧関係からの移行時に向きを検証します。

### 4.2 単なる線では足りないアクセス経路

アクセス経路は `targetRef`、目的、必要条件の式、適用条件、待機・期限、根拠、利用確認を持ちます。必要条件は `allOf` / `anyOf` / 対象参照で表し、循環参照でも処理が終了する必要があります。

例は設計説明であり、各提供者の全状況をこの式だけで確定するものではありません。

- パスワード方式: `ALL(パスワードへアクセス, ANY(そのサービスが認める追加認証))`。
- パスキー方式: `ALL(当該Accountへの登録, 秘密の保存先へアクセス, 必要な利用者確認, 対応環境)`。
- 暗号化バックアップ: `ALL(ファイルへアクセス, 解除手段へアクセス, 互換性のある復元先)`。
- 人が支援する復旧: `ALL(事前の承認完了, 待機期間終了, 相手が対応可能, 提供者の追加確認)`。

現在使えるセッションがある状態、新端末からのサインイン、端末再起動後、全端末を失った状態を分けます。今はオフラインで開ける保管庫でも、新端末で取得できるとは扱いません。循環があっても、独立した有効経路や既存ローカル状態で進める場合があるため、「循環あり＝必ずロックアウト」と表示しません。

### 4.3 状態と根拠

作業の実施記録、設定されたと本人が確認した記録、現在の利用可否、紛失・失効、未確認を分けます。招待済み、受諾済み、本人の確認待ち、待機中、利用可能、失効、利用不能、未確認も区別します。過去の完了を消さずに、現在必要な再確認へ案内します。

紛失シミュレーションは、端末、同じバッグ内のキー、同じクラウドへのアクセス、回線停止、保管庫利用不可、家族・管理者が応答できない場合を対象にできます。独立性は、別のアプリ名やコピー数ではなく、本人が確認した共通の障害・認証・復元条件から判断します。条件が不明なら「影響の可能性」「予備は未確認」と表示します。

### 4.4 対策の有効範囲

本人が確認する対象には、ログイン経路だけでなく、ログイン後に使えるセッション、許可済みの外部アプリ、共有リンク、バックアップの閲覧権限も含めます。MFAを設定したことを理由に、これらを点検済みにしません。

技術解説は、パスワードの使い回し、フィッシング、解除された端末の盗難、保管庫の漏えい、許可済みアプリの悪用、共有先へのコピー、同期された削除・ランサムウェアによる喪失で、何を守れるかが異なることを説明します。対策の有無から、侵害されていないことを推定しません。特に、失効で将来のアクセスを止めることと、既に取得された情報を取り戻すことを分けます。

## 5. Googleの必須経路と境界

### 5.1 見落としていた製品固有の条件

GoogleのAccount、Gmail、Password Manager、Authenticator、Chromeプロフィール、Android端末、Googleによる他サービスへのログインを別の役割にします。利用者が同じAccountだと確認した場合は、基盤MFAの記録を再利用します。

公式資料で、復旧連絡先は復旧メールと別の仕組みで、対象外Accountと利用開始までの待機があることを確認しました。電話の変更も即時に新しい復旧手段になるとは限りません。Google Voiceだけへの依存も点検します。[G04・G05]

パスキーには、本人が作成したものとAndroidによる自動登録があり、削除経路が異なります。Account側の登録とマネージャーに保存された秘密の処理を分けます。[G02]

Advanced Protectionでは、通常の2段階認証とは使える認証・アプリ・復旧の条件が異なります。一般的なバックアップコードやアプリ用パスワードの経路を、そのまま割り当てません。[G03・G06]

### 5.2 経路・受け入れ条件

各行の経路は、全体仕様の一画面一操作・具体的表示・完了条件・戻る・後回し・例外・日英の契約を満たす必要があります。

## 6. Appleの必須経路と境界

### 6.1 見落としていた製品固有の条件

Apple Accountの標準2FA、Security Keys、Recovery Key、Recovery Contact、Legacy Contact、端末のパスコードは別の役割です。Recovery Keyを有効にすると標準のアカウント復旧が置き換わるため、すべての利用者へ無条件に有効化させません。[A01〜A04]

Security Keysは少なくとも2本と適合する機器・ソフトウェアが必要で、子ども・Managed Apple Account等の対象外があります。使っている全端末、Windows・Watchの条件も扱います。[A02]

Advanced Data ProtectionはAccount全体の条件・復旧・地域を確認して選ぶ任意経路です。すべてのiCloudデータが同じ保護になるとは表示しません。Mail・Contacts・Calendarsの暗号化範囲は別です。[A05・A06]

ADPは、復旧の準備→全端末の条件→地域・Account条件→対象データと共有の限界→本人の選択→有効化→状態確認→必要ならWebアクセスの確認、の順です。Webアクセスの停止は故障とは限りません。[A05・A06]

FileVaultの復旧キーはApple Accountの復旧キーと別です。また、iPhone等の暗号化ローカルバックアップの解除情報も別です。新しいバックアップ用パスワードを作れても、古い暗号化バックアップが開けるようにはなりません。保存先と鍵の対応を保持し、別の復旧キーで代用できるとは説明しません。[A12]

## 7. Bitwardenの必須経路と境界

### 7.1 見落としていた製品固有の条件

## 8. 削除・失効・移行・承継の契約

### 8.1 操作の種類を分ける

| 操作 | 意味 | 完了しても保証できないこと |
| --- | --- | --- |
| Mapの記録を削除／非表示 | このアプリ内の記録を消す・隠す | サービス側の設定・権限・秘密が消えること |
| クライアントのアンインストール | アプリの利用場所を削除 | サーバー登録、別端末、バックアップ、外部権限の失効 |
| サインアウト・セッション失効 | 指定された認証済み状態を終了 | 既にコピーされたデータの回収、全方式の失効 |
| サービス側の鍵登録を失効 | そのサービスが鍵・パスキーを受け付けなくする | 保存先の秘密の削除、他Accountへの登録解除 |
| 保存先から秘密を削除 | マネージャー・端末側の当該情報を削除 | サービス側の登録解除、同期済み別コピーへの即時反映 |
| 外部アプリの権限解除 | その権限による将来のアクセスを止める | 既に取得されたデータの削除、外部Accountの削除 |
| 復旧情報・識別子を置換 | メール・電話・鍵等の役割を変更 | 即時有効化、旧値の即時失効、別サービスの更新 |
| 同期データの削除 | 対象の同期集合から削除 | 独立バックアップやエクスポートからの消去 |
| ファイル・バックアップの削除 | 特定のコピーを削除 | クラウドごみ箱・履歴・他コピーからの完全消去 |
| Account・サービスの削除 | 提供者が定める範囲の終了 | 他社Account・有料契約・共有先コピーの同時終了 |
| 物理キー・端末のリセット | 本体の登録情報・鍵等を初期化 | サービス側の登録一覧の整理、消える鍵の復元 |
| 承継・組織からの離脱 | 所有・管理・共有権限を変更 | 全データの譲渡、Keychain等の秘密の承継 |

### 8.2 実行前・実行中・実行後

1. 何をどこから消す・失効するのかを、対象名・役割・操作の範囲で示す。
2. Account・データ・復旧先・共有・下流SSO・他のキー登録・購読への影響を、記録した関係から確認する。未確認も示す。
3. 本人の権限・所有者・組織の条件を確認する。
4. 新しいアクセスと独立した復旧、必要なデータ・所有権の移行を先に確認する。盗難・侵害時の緊急失効は、通常の移行と別の優先順序にする。
5. 取消可能か、猶予・待機・同期遅延があるか、不可逆かをその操作に合わせて示す。
6. 実行は本人が公式の画面で行う。最終的な消去操作をアプリが自動代行しない。
7. 指定した範囲で失効・削除・移行後の状態を確認する。オフラインで未反映のものは保留で残す。
8. 作業の履歴と現況を更新する。新コード発行、失った予備、必要な再登録を一元的に反映する。

このアプリ内の「完了を取り消す」は履歴訂正です。外部で削除したAccount、失効したキー、変更したパスワードが自動的に戻るとは表示しません。記録を削除する場合も、関連する未完了作業を黙って安全扱いにしません。

保存形式は既存v1封筒と暗号化互換性を維持し、データモデルの移行版は封筒とは別に管理します。移行は原本の保持、参照整合性、再実行の安全性、途中失敗時の復帰を必要とします。新しいコードで旧データを生成し直すだけでなく、実際の旧形式フィクスチャで読み書きの保持を確認します。

未対応の新しいモデルを旧コードが読み書きして情報を落とさないよう、互換性を壊す変更ではpayloadの版を明示します。新コードは既存v1を移行して読める一方、解釈できない新形式は変更保存しません。追加項目を未定義キーのまま旧版へ書き戻して、黙って消える設計は採用しません。未知の利用者データは隔離して保持し、HTMLとして描画したり、AIプロンプトへ自動採用したりしません。

監査時に見つかった未知項目の除去に対し、対応するv1の未定義項目の保持、新形式の拒否、開けない元ファイルの退避を実装しました。旧JSONを現在のスキーマへ通さず暗号化したフィクスチャで、通常保存・パスフレーズ変更と、復元失敗時に原本が変わらないことを検証します。これは全将来形式を解釈・移行できることの証明ではありません。

## 10. 確定前の条件と実装順序

1. 本追補を全体仕様・製品別仕様・不足点レビューへ結び付ける。
2. 種別・Account・方式・保存先・権限・アクセス経路を表現する論理モデルと移行契約を先に固める。
3. Google・Apple・Bitwardenの基準経路を、そのモデルへ対応付ける。
4. 同時に必要な条件、代替経路、失効・削除、共有、待機のテストをモデルに追加する。
5. 一画面一操作へ分割した日英のレシピと、確認済みの設定入口・メニュー名を登録する。

仕様書の設計上の不足を補ったこと、資料を確認したこと、レシピを実装したこと、アプリ経路をテストしたこと、実機で照合したことを別々に報告します。残る資料相違や実画面の未確認を隠して「全シナリオ検証済み」「完全」と表示しません。
