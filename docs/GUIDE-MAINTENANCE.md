# 手順カタログの更新

`PRODUCT-SPEC.md` が製品全体の要件、`IMPLEMENTATION-STATUS.md` が現在の対応・検証範囲です。

パスワード管理・認証アプリの製品別契約は `PASSWORDS-AUTHENTICATORS-SPEC.md`、Google・Apple・Bitwardenの境界・到達モデル・削除は `MAJOR-PLATFORMS-MODEL-AUDIT.md` を併用します。`SPEC-GAP-REVIEW.md` から不足と受け入れ条件を追跡します。

`DEVICE-CHANGE-LIFECYCLE-SPEC.md` は、通常のガイドと別に必要時だけ起動する機種変更・旧端末の継続利用・譲渡・売却の契約です。主ガイドの途中位置を上書きせず、共通のAccount・認証・バックアップ記録を参照します。

## ファイルの責務

- `src/guideCatalog.ts`: サービス別・端末別の操作、期待表示、日英文言、分岐、公式の操作先、出典・適用範囲・確認日。
- `src/guideEngine.ts`: 安定IDによる途中位置、前提条件、完了・取り消し・後回し、既存記録の引き継ぎ、関係の追加、AI相談文。
- `src/Guide.tsx`: 一つの質問・操作の表示と例外支援。製品固有の設定名を増やすときは、可能な限りカタログへ置きます。
- `src/SecurityMap.tsx`: 同じ作業記録に基づくグラフ、状態の理由、確認した関係、紛失時の影響の可能性。
- `src/models.ts`: v1・v2のデータ本体スキーマ。`src/crypto.ts` の保管庫名・暗号化封筒は変えていません。
- `src/phoneRetention.ts`: 旧端末の継続利用・予備・未定を分け、旧端末のロック・更新・実利用・保管を一操作ずつ定義。OS操作は共通の端末レシピを再利用する。

## 新しい提供者を追加する条件

1. 認証主体を確認します。同じログインで複数サービスを使う場合は、別アカウントを作りません。
2. 公式資料を読み、地域、契約、OS・ブラウザー、個人用・組織用を分けます。
3. メニュー名、QRやコードの登録、復旧の前提、成功条件を確認します。公式文書が曖昧なら、未確認のメニュー名を補いません。
4. 有効化前の復旧・ログイン維持、有効化後の復旧情報保管、既に有効な場合、画面差異、権限不足の経路を作ります。
5. 一つの操作に一つの主ボタンを基本にし、最終確認だけが対象の対策を更新するようにします。
6. 日英両方の文章、出典URL、適用範囲、確認日を設定します。資料確認と実機確認を混同しません。
7. アカウントを選んだだけで完了しないこと、同一アカウントの重複排除、別アカウントへの誤伝播がないことをテストします。
8. スマホ、キーボード、途中再開、例外経路、PagesでE2Eを実行し、対応表を更新します。

## ID・記録の維持

レシピとステップのIDは、タイトルや配列の番号にしません。表示文言だけを変更するときはIDを維持します。操作の意味そのものが変わる場合は、旧IDからの再開先を定義し、過去の完了記録は証拠として残します。

完了した設定は対象IDとコントロールIDで一元管理します。1つのApple Accountのメール・Drive等で設定を共有し、名前が似た別アカウントとは共有しません。新しい説明を配るだけで、既存の`controls`、`actions`、`assessmentAnswers`、旧ワークフローを消しません。

旧端末の用途の確認は `roleEffect` と前提の安定キーを持つ。前提を取り消す場合は派生する用途の確認を撤回し、別の任意作業に確認が残れば保持する。最後の取り消しでは元のライフサイクルと未知項目を復元する。後から消去・所有移転された端末は復活させない。過去の一画面の `keep-old` 完了は保持し、新しく分割した確認へ自動変換しない。

## 出典と画像

出典リンクは実際の操作先とは別です。通常フローはカタログの説明だけで進めます。図解はアプリが作成した操作の順序図で、「実画面ではありません」と表示しています。現時点で、第三者の設定画面を再配布したり、架空のスクリーンショットを生成したりしていません。

実画面画像を追加する場合は、取得元、再利用条件、OS・版、取得日、代替文、個人情報・認証情報のマスク内容を同じ変更に含めてください。権利・実画面の根拠が確認できない画像は採用しません。

## 検証

```sh
docker build --target checks -t cyber-security-map:checks .
docker build --target browser-tests -t cyber-security-map:browser-tests .
docker run --rm --shm-size=1g cyber-security-map:browser-tests
docker run --rm --shm-size=1g cyber-security-map:browser-tests npm run test:pages
```

公式側にログインして設定を変えるテストは、本人が管理するテスト用アカウントで別に実施します。リポジトリのE2Eが通ったことを、その代わりの証明にしません。

## 主要プラットフォームとモデルの変更

- サインイン、追加認証、復号、ローカル解除、セッション、外部権限を一つの`mfa`へ集約しません。レシピが満たす役割と前提を宣言します。
- 同時に必要な条件・代替経路・待機・組織の条件を失う二項関係への変換をしません。紛失時の評価は状況と未確認を保持します。
- 実施の履歴と、失効・紛失後の現況を別に更新します。記録の取り消しで外部の削除を取り消したことにしません。
- 移行前の原本、未知項目、参照、モデル版を検証します。旧コードが新形式を変更保存して捨てることを防ぎます。
- 公式資料が相違する場合は双方の適用条件を記録し、未照合のOS・機能を対応済みにしません。検索抜粋だけの確認と本文・実機照合も区別します。


## データ本体v2と機種変更の更新

- 暗号化封筒のformat、KDF、暗号方式、IndexedDBの名前は維持する。データ本体の `version: 2` は封筒の版と別。
- v1は通常のガイドでそのまま読み書きできる。v2の機能を初めて使う際に、ID・既存回答・主ガイド・不明項目を保持して変換する。v1に同名の不明な `securityModel` / `deviceWorkflows` があれば変換を止め、元のデータを変更しない。
- `src/securityModel.ts` は追加の型付き実体、関係、利用条件、観測、ライフサイクル。既存Account・Device・Backupを複製しない。参照不整合を検出し、ALL/ANY、文脈、待機、期限、共通障害、循環を区別する。未知の関係や未知の観測から利用可能を推測しない。
- `src/phoneSchemas.ts` は任意作業の保存形式、`src/phoneCatalog.ts` は日英の説明と分岐・出典、`src/phoneEngine.ts` は純粋な遷移と記録、`src/PhoneGuide.tsx` は表示と操作。通常ガイドの保存位置を書き換えない。
- `src/controlRecords.ts` は通常ガイド・任意作業で共用する実施記録。一つの設定の最初の確認前状態を保持し、他の確認が残る間はその設定を取り消さない。最後の確認を取り消すと元の状態と回答へ戻す。
- 機種変更の確認キーは作業ID・安定したステップID・対象ID・意味の分岐で作る。説明文の言い換えでは記録を失効させない。対象端末を変更した場合、別端末の利用確認を流用しない。
- 消去・所有移転は、先行する全必須操作に本人の確認があり、未対応分岐がない場合だけ実行手順へ進む。画面上の無効化に加え、遷移関数でも条件を検査する。
- 観測した新端末ログインと保管庫の復号を別の経路として記録する。MFAの設定完了や、認証コードの保存場所を推測で追加しない。
- 破壊的な現実の操作は、記録の取り消しで元に戻らない。消去済み旧端末を予備の認証手段として自動復帰させない。
- 型付き記録や別作業から参照される項目のローカル削除は、現在は理由を示して停止する。参照が残ったまま保存したり、他の記録を黙って削除したりしない。依存の整理・履歴のアーカイブを伴う削除UIは追加対象。

手順追加時は、通常URLとプロジェクト配下URLの両方で、主ガイドへの復帰・途中再開・旧v1変換・未完了時の消去ガードを検証する。条件木は深さ64、ノード4096まで。上限を超える入力は利用可能と扱わず、読込み・評価を停止する。

端末が紛失・利用不能になった時点や消去した時点を `accessResetAt` として保持する。その後に端末を再利用・予備へ戻しても、その時点以前の利用観測を利用可能へ自動復帰させない。新たな利用確認が必要。機種変更から既存の型付き観測・ライフサイクルを更新するときも、未知の付随項目は残す。

## 組込みパスワード管理の追加

- `src/nativeManagers.ts` は、実際の基盤Account、保管庫、物理端末ごとのアプリ実体と前提条件を扱う。別Account・別ローカルプロフィール・別端末の確認をコピーしない。
- `src/nativeManagerCatalog.ts` は、Apple／Googleの操作・OS差・保存方式差・既存の固有パスワードを変更しない分岐を定義する。外部の操作名や保存先をUIで推測しない。
- `src/subjects.ts` は共通の作業記録を既存Account・型付き実体へ適用する。表示用の一時データを、偽のマネージャーAccountとして保存しない。
- `src/nativeObservations.ts` は確認された操作だけで関係・利用観測を作る。ログインと保存内容の読み取りを分け、通常利用の成功を全端末喪失からの復旧としない。取り消しでは参照される観測・経路を残して未確認へ戻す。
- `src/securityMapViews.ts`・`src/AccessChecks.tsx` は型付き実体の描画用変換、本人が確認した関係、文脈ごとの利用記録を共有する。保管庫の完了表示は、同じ一つの端末上で必要な確認が揃った記録を根拠にする。
- 主ガイドの `native-password:<installationId>` は端末上の実際のアプリ実体に結び付ける。機種変更では主ガイドの回答・途中位置を変更せず、専用回答から新アプリ実体を参照する。
- 同じ物理端末のロックを二度要求しない際も、現在のカーソル・自分の確認記録を消して進行不能にしない。実装範囲と一次資料の確認方法は `BUILTIN-MANAGERS-GUIDE.md` を参照する。

## 認証アプリと実体の再利用

- `src/authenticatorGuide.ts` はアプリ製品・OS・保存方式・準備条件・今回のコードの操作を定義する。`src/AuthenticatorQuestions.tsx` が必要時の質問、`src/authenticatorObservations.ts` が確認した関係・登録観測・取り消しを扱う。詳しい適用範囲は `AUTHENTICATOR-GUIDE.md`。
- 製品を選んだだけ、アプリでコードが表示されただけでは、対象Accountの設定を完了しない。スキャンとサービス側確認を同じ登録操作へ結び付ける。後日の有効状態の確認だけで、コード受け付けの観測日時を更新しない。
- 登録時の確認は `enrollment` の文脈に限定する。通常ログイン、新端末ログイン、復元試験へ変換しない。再登録は古いコピーの利用観測を未確認にするが、履歴や外部の認証方法の削除を推測しない。
- アプリ全体の保存状態と、今回の新規コードの保存先を区別する。Microsoft・Bitwardenの新規ローカル経路から、全コードがローカルのみ、またはバックアップなしとは推測しない。
- Googleの同期Accountを本人が確認したら、その実際のAccountの不足する認証・復旧へ案内する。メインメールのIDを変更せず、同じAccountの完了記録を再利用する。
- 同じ実際のAccountの組込み保管庫を再選択したときは、既存の実体を再利用する。確認・関係・履歴がない仮IDだけに `mergedIntoRef` を付け、元のID・未知項目を保持する。循環、異なる製品・端末・保存先への誤った対応付けを保存時に拒否する。
- 公式のバックアップ仕様の変更日は確認する。特にMicrosoft Androidの2027年1月予定変更は、実際のアプリ版・画面に対応する経路を再調査する。予定日だけで新しい方法の動作確認済みと扱わない。

## 認証アプリの機種変更

- `src/phoneAuthenticators.ts` は、登録済みアプリの再利用、追加製品、実際のグループ・同期元、転送・復元・各Accountのコード確認を定義する。`src/phoneAuthenticatorRecords.ts` は実体・関係・利用観測・取り消しを扱う。対象と根拠は `AUTHENTICATOR-PHONE-MOVE.md`。
- 新端末の既存項目が揃っていれば、不要な書き出し・復元を繰り返さない。新端末のコードを失う再インストール・サインアウトを、画面を合わせるために行わせない。
- 正規ログインでコードが受け付けられた記録と、保管庫を読めた記録を分ける。完了済みの同じログインを一般質問の後で繰り返さない。
- 先行確認の安定キーを、依存する確認・コントロール・利用観測に保持する。書き出し→送信→取込み→コード利用の途中を訂正したら、連鎖する派生証拠も未確認へ戻す。参照される利用経路は削除しない。
- 新コードの現在の利用に、移行元の旧端末を機械的に必要条件として入れない。Bitwardenのローカル・個別保管庫のグループも区別し、無関係な全Accountを一括して必要にしない。
- 一時JSONは読取り可能な秘密ファイルとして扱う。内容を本アプリへ入れず、暗号化バックアップと表示しない。削除済みの記録の訂正で、実ファイルが復活したことにしない。再作成した場合は別のファイル実体として残す。
- 大きい認証アプリでも登録済みAccountの数に合わせてガイドを生成し、小さい固定件数の先頭だけを繰り返させない。未登録・未対応のコードは、完了扱いにせず消去前の未完了として残す。

## Proton Pass・NordPassの保守

- `CLOUD-MANAGERS-GUIDE.md`に対応範囲・公式資料・未対応の分岐を記録する。製品名の選択やAccountのログインから、保管庫の復号・MFA・復旧・実利用を推測しない。
- `passwordStoreIdentity.ts`は組込みとクラウドの実際のAccount・保管庫の同一性を共用する。クラウドの別プロファイルは本人が既存の実体を選んだときだけ再利用し、新しい選択で確認済みのアプリを作らない。
- `cloudSources.ts`と各`cloud*Catalog.ts`に説明・操作先・確認日を置く。`cloudManagers.ts`は必要時の質問と環境・準備条件、`cloudRuntime.ts`は安定キー・前提、`cloudObservations.ts`は確認した関係と利用観測を扱う。
- マスターの変更要求は作業ごとのIDを持ち、以前の変更の証拠を再利用しない。前提の取り消しは派生するコントロールと観測にも反映する。現実の変更の時点は取り消して復活させない。
- `passphraseCatalog.ts`はEFFの単語表を利用する準備方法を共用する。原文・帰属・CC BY 4.0・ハッシュを`public/wordlists/ATTRIBUTION.txt`で管理する。実際の語句を本アプリに保存しない。
- 単語表のURLはPagesのBASE_URL配下とし、PWAの対象に含める。通常URL・プロジェクトURL・オフラインで原文の7776行とハッシュを確認する。
- クラウドの基本機能では必要時だけモデルrevision 2へ拡張する。任意のProton追加パスワードではrevision 3へ拡張し、後の機能で下げない。既存revision 1のデータを説明更新だけで変換・再登録しない。非対応revisionの原本を保持する。

## クラウド保管庫の機種変更

`CLOUD-MANAGERS-PHONE-MOVE.md`を対応契約とし、`phoneCloudManagers.ts`に製品別の質問・説明を置く。`phoneEngine.ts`は新端末上の実体の選択・共用する実施記録・前提を扱い、基本ガイドのオブジェクトを保存し直して位置を変えない。単に同じ製品という理由で、別のAccount・端末・プロファイルへ確認をコピーしない。

Accountの認証、保管庫の復号、保存したパスワードの利用を分ける。確認した文脈と、旧端末を使わずに試した範囲を`cloudObservations.ts`で記録する。独立性の追加意味は版付きの識別子がある観測だけで解釈し、古い同名の不明項目を保持する。モデルrevision 1で取り込んだ項目も、この機能の利用・記録の開始時にrevision 2へ拡張する。

同じ端末のロックを参照するときも、その記録キーを後続の前提へ含める。取り消しでは派生する確認・観測を未確認へ戻し、参照される履歴を消さない。旧端末だけで使い続ける選択と、売却時に必要な引き継ぎを区別する。


## Protonの追加パスワード

[専用契約](PROTON-PASS-EXTRA-PASSWORD.md)を保守します。設定選択で完了にせず、Accountの認証、追加Pass秘密の受け付け、保管庫の読取り、保存したサービス用パスワードを別の観測にします。変更は同じ実際のAccountのPass全体へ適用し、他のAccountやAccountのMFAは変更しません。全Passのサインアウトを確定前に説明し、Pass外の秘密・MFA・復旧を先に用意します。最低8文字と十分な無作為の長さの推奨を混同しません。

`protonPassExtraCatalog.ts`のOS別表示、`protonPassExtra.ts`の要求と物理変更の時点、古い設定への誤った復帰の抑止を合わせて検証します。`GuideStep.explanation`は折りたたみの技術説明です。追加パスワードの設定だけをMFAや保存パスワード利用に数えません。完了記録から準備も取り消せます。資料にない追加パスワードの紛失復旧をAccountリセットで代用しません。

NordPassの個人用マスター復旧はnordRecoveryCatalog.tsの説明とnordRecovery.tsの進行・観測を分ける。CLOUD_SOURCESのnordForgotMaster / nordForgotCode / nordBiometricExtension / nordDestructiveResetと既存nordRecoveryが一次根拠。法人・MSPの回復仕様を個人用へ流用しない。環境差、破壊的な全体リセットとの境界、設定済み生体認証、コード発行前後、新マスターの実利用、現在の控え、途中再開、取り消し後の物理変更保持を対にして確認する。


## Nordの個人用Google・Apple接続

[NORDPASS-CONNECTED-SIGN-IN.md](NORDPASS-CONNECTED-SIGN-IN.md)を契約とします。nordSsoCatalog.tsの説明、nordSso.tsの進行・Grant・取り消し、NordConnectionSession.tsxの主ガイド保持、cloudObservations.tsの部分的な利用証拠を合わせて確認します。接続設定／提供元認証／Nord認証／保管庫復号／保存パスワード利用を混ぜません。接続先の正しい本人情報は利用者が確認し、Appleのリレーアドレスから別Accountを推測しません。
