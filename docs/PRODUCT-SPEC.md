# Cyber-Security-Map 詳細プロダクト仕様

版: 2.3 / 作成・公式資料の調査日: 2026-11-13

この文書は目標となる製品全体の仕様である。要件を記載したことと、実装・動作確認が完了したことを区別する。現在の対応範囲と検証結果は `IMPLEMENTATION-STATUS.md` で管理し、未実装のものを対応済みと表示しない。

パスワード管理・認証アプリについては、[製品別補完仕様](PASSWORDS-AUTHENTICATORS-SPEC.md)も必須要件です。Apple組込み、Google、NordPass、Norton、Proton、KeePass系等の製品差、認証アプリの同期・移行・復元、循環依存を追加定義しています。[不足点のレビュー](SPEC-GAP-REVIEW.md)で、元の仕様からの追加理由を追跡します。

[Google・Apple・Bitwardenとモデルの再監査](MAJOR-PLATFORMS-MODEL-AUDIT.md)も必須追補です。認証・復号・セッション・権限・識別子・ハードウェア・削除を区別する到達モデルと、3系統の経路58件・モデル20件・削除と失効12件を追加しています。調査開始時の5分類・4関係だけのモデルを最終仕様とはしません。

[個人の機種変更・旧端末の扱い](DEVICE-CHANGE-LIFECYCLE-SPEC.md)は、通常の基本対策とは別に必要時だけ起動する経路です。新端末の準備・利用確認から、旧端末の継続利用・予備・譲渡・売却・処分までを定義します。36件の追加を含め、全体の受け入れ条件は196件です。

## 1. 製品の目的と成功条件

利用者が自分で調査し、複数の記事を読み比べ、対策の順序を判断する負担を減らす。サービスを選び、一つずつ質問に答え、アプリ内の具体的な案内を実行すると、本人の端末やアカウントに必要な基本対策を進められる。

主役はダッシュボードや診断スコアではなく、実際の設定まで案内する一本のガイドである。アプリは外部の設定を自動変更せず、利用者が公式の設定画面で実施した作業を記録する。パスワード・認証コード・復旧コードを収集する製品にはしない。

次を成功の基準とする。

- 初めての利用者が、外部の説明記事を読まずに、選んだメールサービスの認証を設定・確認し、復旧手段を確保して次の対策へ進める。
- 設定済みの利用者は不要な変更を求められず、現状を確認して進める。
- 中断・画面差異・管理者による制限・非対応環境を、行き止まりや誤った完了にしない。
- 一つの完了操作が、ガイド・作業記録・Security Mapへ同時に反映される。
- 設定手順を更新しても、過去の回答や完了記録を不必要に失わない。
- 選んでいないサービスに関する一般質問を繰り返さない。

## 2. 用語・名称

| 用語 | 定義・表示規則 |
| --- | --- |
| 対策を進める / Continue guide | 主導線。一つの質問または操作を表示する |
| Security Map | アカウント・端末・認証・バックアップ・復旧の関係と、根拠のある未完了事項を図示する画面。利用者との合意によりこの名称を採用する |
| 設定 / Settings | 言語、外観、自動ロック、暗号化バックアップ、保存用パスフレーズを扱う |
| アカウント | 一つの認証主体。同じ提供者でも個人用・仕事用・別契約なら別のIDにする |
| サービス | そのアカウントを使う機能。例: 同じApple AccountのiCloud MailとiCloud Drive |
| 端末 | 本人が区別できるスマホ・PC・タブレットなど。OSが同じという理由で同一視しない |
| 作業記録 | 利用者が設定・確認したという記録。自動検査や安全保証ではない |
| 保存用パスフレーズ | このアプリの保存データだけを暗号化するもの。マネージャーのマスターパスワードと区別する |
| レシピ | サービス、設定対象、OS・アプリ・アカウント種別に対応した、根拠を持つ手順データ |

一般向け画面で「資産」「資産マップ」を使わない。内部の互換性維持のために既存の `Asset` 型や `assets` キーを残すことは許容する。

## 3. 対象利用者と利用環境

### 3.1 主な利用者

1. セキュリティ用語に慣れていない個人。何をすべきか決めることから支援する。
2. 一部対策済みの個人。設定を壊さずに確認し、不足だけを補う。
3. 家族の端末設定を手伝う人。所有者・使用者・承認権限を混同しない。
4. 個人アカウントと職場・学校の管理アカウントを併用する人。
5. 複数メール・複数端末・複数の復旧手段を持つ人。
6. キーボードやスクリーンリーダーで操作する人。

### 3.2 配布と動作

- Docker Composeだけでローカル起動できる。ホストへのNode.js・npm導入を要求しない。
- GitHub Pagesの `/Cyber-Security-Map/` のようなプロジェクト配下で動く。ルート `/` 固定のリンクを生成しない。
- アプリ内ページの再読み込み、深いリンク、PWAのスコープとキャッシュを検証する。
- PC・スマホの縦画面・タブレットで操作できる。横スクロールが必要な図は図の領域内に限定する。
- iOS / iPadOS、Android、macOS、Windows、ChromeOS、Linuxを区別する。OS全般の手順は、メーカー差・OS世代差を確認してから対応を表明する。
- 管理された端末・古いOS・サポート終了OSを、新しい一般向けOSの手順へ無条件に流さない。
- オフラインでは保存済みの手順と記録を閲覧できる。サービス側の設定変更に接続が必要なことを、その時点で示す。

## 4. 情報設計

主メニューは「対策を進める」「Security Map」「設定」の3つとする。旧ページを維持することを優先して操作を重複させない。旧URLは可能なら新しい該当導線へ案内し、保存データや作業記録の削除を伴わせない。

### 4.1 初回

1. ガイドの目的を短く表示し、「対策を始める」を主操作にする。
2. 作業を途中保存するための、このアプリ専用の保存用パスフレーズを設定する。
3. 暗号化保管庫を作成したら、すぐによく使うメールの選択へ進む。
4. 関心事・家族構成・全端末・全サービスなどの大量登録を先に要求しない。
5. 旧データがある場合は保管庫を開く。再登録を要求しない。旧バックアップの復元も初回画面からできる。
6. 保存用パスフレーズを忘れると、暗号化バックアップだけでは開けないことを正確に説明する。

### 4.2 ガイドの順序

基本は、主なメール → 復旧の備え → パスワードマネージャー → 重要なログインの生成・保存・利用 → 端末のロック・バックアップ・更新 → ほかの重要アカウント、とする。

これは固定チェックリストではない。回答と既存記録により不要な作業を省く。認証変更に必要な復旧手段は変更前に確保する。新しい認証が使えることを確認する前に、古い方法を削除する案内は出さない。復旧手段が確保できない場合、パスワード変更やログアウトへ進ませない。

### 4.3 各画面の契約

| 項目 | 必須条件 |
| --- | --- |
| 対象 | どのアカウント・端末に対する作業か、秘密情報なしで分かる |
| 見出し | 一つの質問、または実行する一つの操作を述べる |
| 今すること | 具体的な動詞で書く。「適切に設定」だけで済ませない |
| 操作場所 | OS設定、アカウントWeb設定、認証アプリなどを明示する |
| 押す項目 | 実際に確認した表示名を使う。表示言語が違う場合は公式の英語表記も併記する |
| 期待される表示 | 成功時に何が見えるか、または何を操作できるかを示す |
| 次へ進む条件 | その操作が終わったと判断できる観察可能な条件を書く |
| 主ボタン | 「次へ」「設定しました」「確認しました」「ログインできました」など、意味に合う言葉を選ぶ |
| 外部リンク | 可能なら公式の設定画面へ直接リンクし、別タブで開いて戻れるようにする |
| 例外 | 「うまくいかない」から、その場の条件に合う分岐を開く |
| 補足 | 根拠・確認日・詳しい仕組みは折りたたみ、主操作の近くに長文を並べない |

長い設定を「画面の案内に従う」一枚へ丸めない。メニューを開く、方法を選ぶ、QRを登録する、公式画面へコードを入力する、復旧情報を保管する、動作確認する、を必要に応じて別ステップにする。公式側に動的な本人確認がある場合、その本人確認を公式画面で進めることと、戻る先・完了条件を示す。

## 5. サービス選択とアカウントの識別

### 5.1 選択の規則

- 表示名、アイコン、俗称、旧ブランド名でも提供者を探せるようにする。検索文字列にメールアドレスを要求しない。
- 例: Gmail / Google、iCloud / Apple Account、Outlook / Microsoft、Proton Mail、Tuta / Tutanota。
- 独自ドメインのメールでは、ドメイン名ではなく実際の提供者・管理者が設定を決める。「独自ドメインだから非対応」としない。
- 「自分のメールサービスがない」を常に用意する。確認済み手順の追加候補として扱い、似た名前の提供者の手順へ流さない。
- Yahooの国別運営（Yahoo.comとYahoo! JAPANなど）は別提供者として扱う。
- GmailとGoogle Workspace、個人用Microsoftと職場のMicrosoft 365は管理条件を区別する。
- 同じ提供者に複数アカウントがある場合は明示的に選択する。表示名の一致で結合しない。

### 5.2 共通の認証フロー

1. 本人が設定対象のアカウントでログインしていることを確認する。
2. 現在のログインを維持する。
3. 復旧用メール・電話・復旧コード・予備キーなど、変更前に使える手段を確保する。
4. 認証の現在の状態を確認する。
5. 有効なら、設定を変えずに確認へ進む。
6. 無効なら、提供者で確認済みの方法を選ぶ。
7. 方法に合う登録手順を一つずつ案内する。
8. 発行された復旧情報は、このアプリ以外へ安全に保管する。
9. 認証が有効であることを公式設定で確認する。
10. 必要な場合は既存セッションを残し、別ウインドウ等で新しいログインを試す。
11. 一回の主ボタンで作業を記録し、次の必要な対策へ進む。
12. 認証を保持する端末、独立した予備手段の存在は別に質問し、確認した関係だけをMapへ追加する。

サービスによって「復旧用情報の生成が認証有効化後になる」場合がある。その場合も事前にログイン維持と既存の復旧手段を確保し、有効化直後にコードを保管し、保管前にログアウト・既存手段の削除へ進ませない。

## 6. 対応カタログと調査契約

対応数を見せるために未確認の手順を追加しない。各セルは `調査候補 / 公式資料確認済み / アプリ内手順実装済み / 経路テスト済み / 実機画面確認済み` を独立して記録する。「公式資料確認済み」は実際のアカウントで設定を実行した意味ではない。

### 6.2 iCloudの必須経路

| 順序 | iPhone / iPad | Mac | Web |
| --- | --- | --- | --- |
| 1 | 「設定」を開く | Appleメニューから「システム設定」 | `account.apple.com` を開き本人がサインイン |
| 2 | 自分の名前を選び対象Accountを確認 | 自分の名前を選び対象Accountを確認 | 対象Accountを確認 |
| 3 | 「サインインとセキュリティ」 | 「サインインとセキュリティ」 | 「サインインとセキュリティ」内のアカウントセキュリティ |
| 4 | 現在の2ファクタ認証を確認 | 同左 | 現在の状態またはアップグレード操作を確認 |
| 5 | 有効なら変更せず確認 | 同左 | 同左 |
| 6 | 無効なら2ファクタ認証をオン | 同左 | 公式のアップグレード操作 |
| 7 | 本人が受信できる電話番号の確認を公式画面で進める | 同左 | 同左 |
| 8 | 有効な状態を確認して記録 | 同左 | 同左 |
| 9 | 独立した予備の信頼できる電話番号を確保 | 同左 | 同左 |

公式の根拠: [Apple 2ファクタ認証](https://support.apple.com/ja-jp/102660)、[信頼できる番号・端末](https://support.apple.com/en-us/122621)。公式資料確認日: 2026-11-13。旧OSで表示が違う場合は、確認済みのWeb経路へ切り替えるか、そのOS向けの検証済みレシピを選ぶ。

同じApple AccountのメールとDriveで、認証を二度設定させない。別のApple Accountは別記録とする。本人がその端末を信頼済み端末として確認するまで、「認証に使う」という線を推測で描かない。

### 6.3 Googleの必須経路

Google Accountの「セキュリティとログイン」→「Google にログインする方法」→「2 段階認証プロセス」を基準にする。通知・TOTP・パスキー・キーのうち、現行の公式資料と端末条件で案内できる方法を分岐させる。

Googleからのメッセージでは、今自分が始めたログインだけを端末情報を見て承認する。バックアップコードは有効化後に生成・印刷・保管し、再生成すると古いコードが無効になることを操作時に知らせる。Workspaceで許可されない場合は管理者確認へ分岐する。

根拠: [Googleの2段階認証](https://support.google.com/accounts/answer/185839?hl=ja)、[バックアップコード](https://support.google.com/accounts/answer/1187538)。確認日: 2026-11-13。

### 6.4 Protonの必須経路

1. `account.proton.me` の本人のアカウントへサインインする。
2. Settings → All settingsを開く。
3. Account and passwordを選ぶ。
4. Two-factor authenticationのAuthenticator appの状態を確認する。
5. 既存セッション・利用可能な復旧手段・独立した認証アプリを確保する。
6. 未設定ならAuthenticator appをオンにし、公式画面で本人確認する。
7. 表示されたQRを独立した認証アプリへ登録する。QRや秘密鍵をこのアプリへ渡さない。
8. Nextへ進み、要求されたパスワードと認証コードをProtonの画面だけに入力してSubmitする。
9. 発行された一回用の復旧コードを印刷または安全に保管する。
10. 有効な状態と別ウインドウからのログインを確認して記録する。

既に有効な利用者に、認証アプリを増やすためだけに無条件でオフ→オンを要求しない。リセット・再登録は別の保守作業として、復旧を先に確保してから扱う。Protonのアカウント復旧、2FA復旧、暗号化済みデータの復旧を同じものと説明しない。

根拠: [Proton認証アプリ2FA](https://proton.me/support/2fa-authenticator-app)。確認日: 2026-11-13。

### 6.5 Fastmailの必須経路

Settings → Privacy & Securityの中で、最初にAccount recoveryから利用可能な復旧電話を登録・確認する。Password & Two-step verification → Manage two-step verification → Add verification deviceで方法を選ぶ。TOTPの場合はQR登録、コード確認、端末の呼び名の設定を分割する。復旧コードはAccount Recovery画面で安全に控える。メールクライアントにアプリ用パスワードが必要な場合は、その作業を別に案内する。

根拠: [Fastmail 2FA](https://www.fastmail.help/hc/en-us/articles/360058752374-Using-two-step-verification-2FA)。確認日: 2026-11-13。

## 7. 認証方式ごとの仕様

### 7.1 TOTP認証アプリ

認証アプリの導入、アプリを開く、サービスのQRを表示する、認証アプリの追加操作、QRまたは手入力による登録、生成されたコードを公式画面へ入力する、復旧手段の保管、動作確認を区別する。同一スマホでQRを読めない場合は、確認済みの手入力経路または別端末で表示する経路を案内する。

認証アプリ候補と製品別の必須経路は、[補完仕様A1〜A5](PASSWORDS-AUTHENTICATORS-SPEC.md#a1-認証アプリの対応候補と違い)を正とする。Google、Microsoft、Apple、Proton、Ente、2FAS、Aegis、Bitwarden、Authy、Duo、Yubico等に加え、組織・サービス専用の方式も扱う。OS、バックアップ・同期、端末紛失時の復元、製品自体の保護方式をレシピ化してから対応する。

パスワードマネージャー自身のTOTPを、そのマネージャーだけの中へ保存させない。同期された認証アプリが依存するアカウントも、本人が確認した場合だけMapへ追加する。

### 7.2 パスキー

端末の画面ロック、対応OS・ブラウザー、保存先、同期先アカウント、別端末で使う方法、端末紛失時の利用可能性を確認する。同期パスキーと端末にだけあるパスキーを混同しない。登録後、公式画面の登録一覧と実際のログイン成功を確認する。古いパスワードや認証を消す手順は通常の追加経路に含めない。

### 7.3 物理セキュリティキー

サービスが対応する規格、USB/NFC等の接続、OS・ブラウザー対応、必要なPIN・タッチ操作を確認する。可能なら独立した予備キーを先に確保し、2本を同じバッグに保管することを「独立」と扱わない。キーのシリアル番号やPINは収集しない。

### 7.4 SMS・音声・通知

利用できる現行の公式方式だけを表示する。電話番号へのアクセスとSIM再発行、通知の承認対象、番号の変更時の注意を必要な操作に合わせて説明する。SMSだけの対応を「フィッシングに強い」と表示しない。提供者が方式を廃止している場合は、新規設定の選択肢に残さない。

### 7.5 パスワードレス・SSO

通常のパスワードがないアカウントにパスワード変更を強制しない。基盤のApple・Google・Microsoft・組織IdPが認証を担当する場合、依存関係を確認し、同じ認証設定を重複させない。組織の規則を回避する案内は禁止する。

## 8. パスワードマネージャーを使える状態にする

### 8.1 対応製品の計画

製品候補と製品ごとの到達条件は、[補完仕様P3〜P9](PASSWORDS-AUTHENTICATORS-SPEC.md#p3-パスワードマネージャーの対応候補)を正とする。Apple・Google等の組込み機能を、外部製品と同じく正式な選択肢にする。Bitwarden・1Passwordの初期実装だけで仕様の完了とはしない。アカウント型・ローカル型・OS組込み型・ブラウザー型・組織管理型を区別する。

「その他」を選んだ人に、新しい製品の導入や乗り換えを強制しない。既存マネージャーを使う場合にも、その製品で確認済みの復旧・保護・保存・利用の手順が必要である。未対応は未対応と明示する。

### 8.2 共通の到達条件

1. 選択した端末・ブラウザーで公式アプリまたは拡張機能を導入できる。
2. 既存アカウントを再利用するか、新規作成するかを選べる。
3. サーバー地域、セルフホスト、組織アカウントの違いを扱う。
4. 製品が独立したマスターを必要とする場合にだけ、固有で強いマスターパスワード／パスフレーズを用意する。Apple・Google等には架空のマスター作成を要求しない。
5. 製品の最低条件、外部サービスの制約、ガイド独自の推奨を区別し、数値の根拠・適用対象を記録する。端末のPINへマスター用の文字数を流用しない。
6. ランダムな単語を使う場合、実際の生成機能、単語数、区切り、生成し直す操作を説明する。歌詞や自分で関連語を並べる方法をランダム生成としない。
7. 画面の例や公開の例文をそのまま使わせない。アプリ内で利用者の秘密を生成・収集・記録しない。
8. 紙の控えは、端末と別の施錠できる場所へ保管する。唯一の控えを当該保管庫の中に閉じ込めない。
9. Emergency Kit、Secret Key、復旧コード、緊急アクセス等の製品固有の情報を正しく扱う。
10. 製品の認証構造に合う保護を設定・確認し、独立した認証・復旧の備えを確保する。OS組込みの基盤Accountの既存MFAを再利用し、ローカルDBへ存在しないアカウントMFAを要求しない。
11. 現在の重要アカウントのログインを先に保存する。
12. 変更が必要な場合にサービス側の正しいパスワード変更画面を開く。すでに固有で適切なパスワードを保存・利用できる場合は、不要な変更を強制しない。パスワードレスも別に扱う。
13. 固有の新しいパスワードを製品の生成機能で作り、サービスの文字数・文字種制約に合わせる。
14. サービス側の変更成功とマネージャーの更新を両方確認する。失敗した場合に古い情報を失わない。
15. 保存した情報を使ってログインできることを確認する。
16. その後に次の対策へ進む。「インストールした」だけでマネージャーの利用準備が全部終わった扱いにしない。

Bitwardenの最低12文字という条件と、長いランダム語列の推奨を区別する。1PasswordのEmergency Kit・Secret Keyと、このアプリの暗号化バックアップを混同しない。

機種変更、旧端末の継続利用・予備・譲渡・売却は、通常の基本対策の必須質問にしない。本人が必要なときに始められる別の作業として、[専用仕様](DEVICE-CHANGE-LIFECYCLE-SPEC.md)を満たす。主ガイドの途中位置を保持し、新旧端末のAccount・認証・バックアップ・作業記録は共通のモデルで扱う。

新端末を使えることと、旧端末を手放せることは別の到達条件とする。旧端末を残すときも、用途の選択だけで有効な予備に数えず、ロック・更新・新端末なしでの実利用・保管を一操作ずつ案内する。「まだ決めていない」回答や、故障した端末から利用可能・独立復旧を推測しない。

## 11. 回答・記録・重複排除

### 11.1 一元管理

ガイド、Map、記録一覧は同じデータから派生する。画面ごとに別の「設定済み」フラグを持たない。完了と次への移動は、一つの保存処理として扱う。保存失敗時には進めず、成功したと誤表示しない。

### 11.2 識別キー

- アカウントID: 提供者名ではなく、一つのログイン主体の不変ID。
- 端末ID: OS名ではなく、一つの端末の不変ID。
- 対策キー: 対象ID + 設定の意味を表す安定ID。文言やステップ番号をキーにしない。
- 手順位置: レシピID + 安定したステップID。途中の説明追加で別の操作へずれない。
- 認証設定の共有: 本人が同一アカウントと確認したサービス同士だけで共有する。
- 別アカウント: 名称が一致しても、明示的な選択なしで結合しない。

### 11.3 状態

未確認、対応が必要、実施した、確認した、後回し、該当しないを区別する。サービス選択は設定完了ではない。後回しも完了ではない。未対応は該当しないと同義ではない。

完了操作を取り消せる。取り消しでは以前の状態・根拠・回答を復元する。他のサービスや別アカウントの完了を巻き戻さない。説明の更新だけで記録を全消去しない。

### 11.4 中断・変更

各質問の確定、各操作の完了、後回し、戻る、分岐変更を暗号化保存する。再読込・ロック・タブを閉じた後は保存済みの同じ位置から再開する。保存中は状態を明示し、連打による競合書き込みを防ぐ。保存成功前に閉じた場合、最後に保存できた位置へ戻る。

回答を訂正したとき、無関係な記録は保持する。端末を切り替えても同じアカウントの認証を最初から無条件にやり直さない。提供者・認証主体そのものが変わる訂正では、別アカウントの完了を引き継がない。

## 12. Security Map

### 12.1 ノードと関係

ノードはアカウント、メールの役割、端末、マネージャー、認証アプリ、パスキー・キー、バックアップ、独立した復旧手段などを扱える拡張可能な型とする。秘密の値はノードへ入れない。

関係には「復旧先メール」「この端末で認証する」「バックアップの保存先」「同期先」「独立した予備手段」など、意味のある型を持たせる。矢印の向きの意味を凡例または選択詳細に示す。図の線だけでは分かりにくい場合、同じ関係を文章の一覧でも読むことができる。

登録されたものが同じサービスに見えるだけで線を引かない。設定した端末だから、その端末に認証アプリやパスキーがあると推定しない。確認していないつながりは未確認として扱う。

### 12.2 色と表示

| 表示 | 根拠 |
| --- | --- |
| 対策が必要 | 本人が未実施や問題ありと回答した重要な対策 |
| 確認待ち | 対策の状態、復旧手段、独立性がまだ確認されていない |
| 作業を記録済み | 対象の必要な対策に本人の実施・確認記録がある |
| 後回し | 明示的に延期された作業。完了と混同しない |

色だけで意味を伝えず、短いラベルと理由を表示する。「安全度100%」「完全に保護」などの根拠のない数値・保証は禁止する。記録済みは「安全」を保証する表示ではない。

### 12.3 操作

- ノードを選ぶと、未確認・未完了の理由、関連するつながり、対策のガイドへの入口がある。
- 端末を失った想定で、確認済みの関係から影響の可能性があるログイン・復旧を表示する。
- 一段先だけでなく、メールが別アカウントの復旧先になっている連鎖も扱う。循環でも無限ループにしない。
- 予備手段が同じ端末・同じバッグ・同じ基盤アカウントに依存している場合、独立性を保証しない。
- 未登録のつながりがないことを、安全である根拠にしない。
- Mapを理解・操作しなくても、ガイドの基本対策は完走できる。
- 新しいノード種別を増やす場合、その情報が利用者の具体的判断や作業にどう役立つかを仕様に加える。

## 13. 例外時の支援

### 13.1 アプリ内で先に解決する分岐

画面が違う、項目がない、対象アカウントが違う、権限がない、管理者が制御している、未対応、電話・メールが使えない、認証コードが合わない、同じ端末でQRを読めない、容量が足りない、通信がない、設定変更が保留されている、セキュリティ待機時間がある、を必要なレシピで扱う。

分岐の選択はその場でできる。やり直し、別端末、確認済みのWeb経路、後回し、管理者確認などの安全な出口を用意する。困りごとの選択を、対策の完了として記録しない。

### 13.2 AI相談

通常の作業にはAIを必要としない。アプリ内の分岐を試して解決しない場合に限り、相談用プロンプトを表示・コピーできる。

含めるもの: サービス、端末・OS、分かっている場合の版、作業、現在の手順、期待表示、選んだ困りごと、公式資料URLと確認日。版が未確認なら未確認と書く。

含めないもの: メールアドレス、個人名、ユーザー名、端末の私的な呼び名、メモ、実際のパスワード、認証コード、QRの内容、復旧コード、Secret Key、秘密鍵、APIキー、トークン。

AIには最新の公式資料を確認し、一度に一つの質問か操作だけを案内し、確認できない場合はその旨を明示するよう指示する。画像を添える場合は秘密情報・個人情報を隠すよう短く案内する。外部AIへ自動送信しない。クリップボードが使えない場合も、表示された文章を手動選択してコピーできる。

## 14. 手順・画像・出典の維持

### 14.1 レシピのデータ項目

| フィールド | 内容 |
| --- | --- |
| レシピID、ステップID | 文言や順番に依存しない安定ID |
| 提供者、認証主体、機能 | 同じアカウントで共有する設定の範囲 |
| 対応条件 | OS・アプリ・ブラウザー・地域・契約・管理条件 |
| タイトル・操作・期待表示 | 日英の自然な文章 |
| 前提条件 | 復旧、権限、利用可能な認証手段、接続など |
| 遷移 | 次、戻る、設定済み、未設定、例外、後回し |
| 完了効果 | どの対象のどの対策を、どの根拠で更新するか |
| 外部の操作先 | 公式設定の確認済みURL。文書URLと区別する |
| 出典 | 公式資料URL、対象範囲、確認日、確認方法 |
| 画像 | ファイル、代替テキスト、権利、検証元、マスク内容、版 |
| 解説 | 仕組み、想定攻撃、有効範囲、限界 |

### 14.2 調査・更新の手順

1. 公式資料を探す。検索結果だけで不明な細部を断定しない。
2. 地域・OS・アプリ・プラン差と、現在の資料の適用範囲を読む。
3. 操作名・URL・成功条件・復旧の前提を記録する。
4. 資料の閲覧確認か、本人のテスト用アカウントによる実画面確認かを区別する。
5. データとUIを分離してレシピを変更する。
6. 安定IDを保ち、説明変更で過去の完了を消さない。
7. 日英両方の文章と分岐を確認し、経路テストを更新する。
8. 対応範囲表と最終確認日を更新する。未確認の枝は対応済みにしない。

定期見直しの目安は90日とし、認証・復旧の重要変更、OS更新、リンク切れ、利用者の画面相違の報告があれば前倒しする。定期自動実行や外部通知は別途利用者が依頼した場合だけ追加する。

### 14.3 画像

複雑な操作対象や機種差が文章だけで伝わりにくい場合に、確認済みスクリーンショット・注釈・強調を使う。権利や再利用条件を確認できない画像をコピーしない。生成した架空の設定画面を実画面として見せない。

説明図は「説明図・実画面ではありません」と表示する。画像なしでも操作・対象項目・完了条件を読めるようにする。個人情報、QRの秘密、パスワード、認証コード、復旧コードを画像へ含めない。画像の版が古いと分かったら非表示にし、テキスト手順と根拠を先に更新する。

## 15. 日本語・英語とアクセシビリティ

- 日本語は直訳を避け、何を押し、何を確認するかが分かる文章にする。
- 英語も同じ作業目的と条件を表す。自然さのために意味や安全条件を落とさない。
- 「セキュリティの現在地」「データはあなたのものです」など、操作や判断を増やさない表現を削除する。
- 同じ注意書きを毎画面で長く繰り返さない。秘密の入力が必要な外部操作など、必要な瞬間に短く示す。
- 技術解説は免責文ではなく、仕組み・具体的な攻撃・有効範囲・限界を説明する。
- キーボードで主操作・戻る・後回し・例外選択・Mapのノード・設定を操作できる。
- ステップ変更時、画面内の現在位置へフォーカスを移し、見出しを見失わせない。
- 操作ボタンは原則44 CSS px以上を確保する。通常本文はスマホで16px程度を基準にする。
- 色に依存せず、テキスト・形・状態ラベルを併用する。フォーカスを視認できる。
- 390pxだけでなく320px幅、拡大表示、長い英語、長い既存の呼び名でも確認する。
- 外部リンクは別タブで開くことを支援技術へ伝え、戻る先が残るようにする。
- アニメーションを必須にせず、動きの低減設定を尊重する。

## 16. 保存・互換性・安全性

既存の `personal-cyber-os` IndexedDB、`encrypted-vault` ストア、v1暗号化封筒形式を維持する。AES-256-GCM、PBKDF2-SHA-256、600,000回以上、ランダムsaltと暗号化ごとのnonceを維持する。パスフレーズ・復号鍵は永続保存しない。

旧データにガイドの項目がない場合は既定値を追加し、既存のアカウントID、端末ID、対策、根拠、回答、作業、ワークフロー、復旧関係、設定を保つ。旧データの提供者を表示名から推測して確定せず、必要なときだけ本人へ聞く。既に実施・確認済みの対策は引き継ぐ。

暗号化バックアップの書き出し・復元、保存用パスフレーズの変更、自動ロックを維持する。復元による置換・消去には対象を明確にした確認を設ける。作業中データを知らずに上書きしない。

外部への自動送信API、分析、広告、第三者スクリプト、外部AI送信は追加しない。公式設定への移動は利用者が押したリンクだけで行う。Mapのラベルはテキストとして描画し、HTMLとして解釈しない。サービスワーカーは静的アプリだけを保存し、保管庫や回答をキャッシュ対象にしない。他のプロジェクトのキャッシュを削除しない。

### 17.2 テストの層

レシピのID・遷移・日英文言・出典の整合性を単体テストする。状態遷移、完了の一元反映、取り消し、重複排除、依存の連鎖・循環、プロンプトの秘密除外を単体テストする。旧形式を新コードで作り直しただけのテストではなく、旧JSONを直接暗号化したバックアップのブラウザー復元を検証する。

E2Eでは利用者と同じ画面操作を通す。外部サービスの実設定を無断変更せず、アプリ内の分岐・記録・再開を検証する。公式資料確認、アプリ経路テスト、実際の端末・アカウントでの実機確認を別の検証結果として報告する。

## 18. 実装順序と完了判定

1. 既存コード・作業中変更・未マージPRを確認する。今回、mainと未マージPR #5の初回文言変更を確認した。
2. この仕様と対応表を作成し、各要件に実装箇所と検証の証拠を対応付ける。
3. 保存・互換性を維持したガイド状態モデルと、完了の一元管理を実装する。
4. 一本のガイド、3メニュー、自然な日英の操作文言を実装する。
5. iCloudの全基準経路を実装し、端末差・設定済み・例外・復旧を検証する。
6. Google・Microsoft・Protonを実装し、小規模メールを公式資料が揃った順に追加する。
7. パスワードマネージャーの導入から重要なログインの利用まで実装する。
8. 端末・バックアップ・更新の手順を追加する。
9. Security Mapと依存の表示、ガイドへの接続を実装する。
10. 旧データ、Pages、Docker、オフライン、日英、スマホ、キーボードを検証する。
11. 対応表とテスト結果を更新してPRを作る。仕様に書いた拡張対象すべてを、初回PRで実装済みと誤記しない。
12. 以降の各拡張も、具体的手順・復旧・例外・出典・経路テストが揃って初めて対応済みへ変える。

仕様の到達目標は、サービス数の多さだけではない。一つの提供者について、利用者が設定と確認を終え、復旧できる備えを持ち、次の必要な対策へ進めることが最小の完了単位である。
